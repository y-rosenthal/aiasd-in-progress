Classes 10–12: Task App Architecture — Why Each Piece Is There

All steps · Start here

This page explains why the task app is set up the way it is. It walks through every entry on the setup worksheet and every command you run, in worksheet order, and says what each one is for. It does not repeat the setup steps: for what to click and type, follow the step pages, starting at Start here.

Created November 17, 2026. The Supabase, Stripe, Google, and OpenAI facts on this page were checked against each service’s official documentation on that date.

Download the Task App Setup Worksheet (Excel)

The whole app in one picture

The app has four homes. The browser shows the pages. Vercel serves those pages once the app is online (on your computer, npm run dev serves them instead). Supabase holds the database, the logins, the image storage, and the Edge Functions. Google, OpenAI, and Stripe each do one job: sign-in, AI labels, and payments. Nothing runs on your computer except the pages while you develop them.

BROWSER — the pages you see (the Next.js app)
   │  1. tasks, sign-in, images
   ▼
SUPABASE (your project) — database · Auth · Storage · Edge Functions
   │  2. Edge Functions call OpenAI (labels) and Stripe (checkout)
   ▼
OPENAI · STRIPE · GOOGLE (sign-in)
   │
   │  3. Stripe calls the stripe-webhook function back
   ▼
SUPABASE (stripe-webhook) — the database marks the user Premium, or not

Three kinds of requests travel through this picture:

  1. The browser talks to Supabase directly for everyday data: reading and changing tasks, signing in, and storing attached images. It sends the publishable key and the user’s login token, and the database’s Row Level Security rules decide which rows that user may touch. See Step C.
  2. The browser asks an Edge Function for any job that needs a secret key: the AI label and the Upgrade checkout. The function checks the login, then uses its secret key on Supabase’s servers, where nobody can see it. See Project Architecture.
  3. Stripe calls the app back. When a payment succeeds or a subscription ends, Stripe sends a message to the stripe-webhook function, which checks Stripe’s signature and updates the user. See Step H.

One rule explains most of the setup: a secret key must never reach the browser, because anything in a web page can be read — and changed — by whoever opens it. So every secret lives on a server (Supabase), and the only keys in the browser are the ones made to be public. The full reasoning is in Publishable and Secret Keys. This app has no Next.js API routes of its own: the three Edge Functions are the only server-side jobs the app needs beyond serving its pages.

The worksheet, row by row

The worksheet’s My Info sheet has one row for each thing you record, in the order below. Yellow cells are values you type. Gray cells are filled in for you by formulas. Rows marked SECRET hold values that must never be shared, posted, or committed to Git. Each group links to the step page that tells you how to fill it in.

Your computer

Your computer: Mac, Windows or Linux. The step pages show three tabs for anything that differs by computer. This row tells you which tab to follow. See Start here.

The app’s code folder (task-app) on your computer. Every npx and npm command must run from inside this folder, because that is where the app’s code and its installed tools live. The row records the folder so you always know where to cd first. See Step B.

GitHub

GitHub username. Your username is part of your fork’s web address, so the worksheet builds the address from it. See Step B.

Your fork’s address (filled in for you). A fork is your own copy of the course’s code, in your GitHub account. The address is built as https://github.com/<your username>/task-app, which is why your fork must be named task-app: any other name would make this built address wrong. The git clone command copies the fork onto your computer. See Step B.

Supabase (database, login, file storage, Edge Functions)

Email you use to sign in to Supabase. This only records which account owns the project, so you sign in with the right one later. See Step C.

Supabase project name. A project is one complete back end for one app: its own database, users, keys, and web address. The name is only a label, so you can find the project in the dashboard. You reuse the same name for the Google and OpenAI projects, so the three stay visibly connected. See Step C.

Database password (SECRET). This is the password of the PostgreSQL database itself. The app never uses it: the app talks to Supabase with API keys. Only tools that connect to the database directly may ask for it — the Supabase CLI, when you link the project or push the database changes. Anyone who has it can read and change all of your data. It is shown only when you create the project, so the worksheet is the one place you keep it. See Step C.

Project ref (Project ID). The ref is the project’s unique ID: 20 letters, and the first part of the project URL. The CLI uses it to know which project a folder belongs to, and the worksheet builds four addresses from it. See Step C.

Project URL (filled in for you). This is the web address of your back end: https://<ref>.supabase.co. The app sends its data requests there, so the address goes in .env.local and, later, in Vercel. See Step C.

Publishable key. This key identifies your project to Supabase and may appear in web pages: on its own it can only do what the Row Level Security rules allow, so one user cannot reach another user’s tasks with it. It goes in .env.local and in Vercel, because the browser code needs it. See Step C and Publishable and Secret Keys.

Secret key. Only for the optional tests. (SECRET) This key skips all Row Level Security rules, so it must never leave the server side and must never go in .env.local or Vercel. Supabase hands it to the Edge Functions by itself — you never enter it for them. Its only manual use is .env.test.local, where the automated tests need it to set up and check test data without the security rules getting in the way. See Step L and Publishable and Secret Keys.

Google sign-in (OAuth) callback URL (filled in for you). When Google finishes signing a user in, it sends the browser back to this address — a Supabase page that receives Google’s answer. The worksheet builds it from the Project URL; Supabase shows the same address on the Google provider page. You paste it into Google as an authorized redirect URI. See Step D.

Stripe webhook URL (filled in for you). This is the web address of the stripe-webhook Edge Function. You paste it into Stripe so Stripe knows where to send payment messages. It belongs to your Supabase project, not to the app’s address, so deploying the app to Vercel never moves it. See Step H.

Your project’s dashboard (filled in for you). The dashboard address, built from the project ref. It is only a bookmark: the place you return to for settings, logs, and the SQL editor.

Google (“Sign in with Google”, i.e. OAuth)

Google account you use for Google Cloud. This only records which account owns the Google Cloud project, so you sign in with the right one. See Step D.

Google Cloud project name. Google groups its settings into projects, just as Supabase does. The name is only a label. The app never uses the name or Google’s Project ID. See Step D.

OAuth Client ID. This identifies your app to Google: when Supabase sends a user to Google’s sign-in page, the Client ID says which app is asking. It travels in the sign-in page’s address, so it is not a secret — but it lives in Supabase’s settings, not in .env.local, because Supabase (not the browser) is the one that presents it to Google. See Step D.

OAuth Client secret (SECRET). This proves to Google that a request really comes from your app: when Supabase exchanges Google’s one-time code for the user’s name and email, it presents this secret. It is shown in full only when you create the client, so copy it at once. It lives in Supabase’s Google settings, never in the browser. See Step D.

OpenAI (AI task labels; about $5 of prepaid credit)

Email you use to sign in to OpenAI. This only records which account owns the API key and the credit. Note that the OpenAI API platform is separate from a ChatGPT subscription: paying for ChatGPT does not buy API credit. See Step E.

Credit you bought ($). The API is prepaid: you buy credit first, and the balance falls as the app uses it. The row records your budget. Keep auto-reload OFF, so OpenAI never charges your card again on its own. See Step E.

OpenAI project name. A project keeps one app’s key and spending separate from anything else on the account. If the key ever leaks, the project name tells you which key to delete. See Step E.

Monthly spend limit you set for the project ($). A second lock, for this project only: with Enforce a hard limit on, OpenAI refuses requests once the project reaches the limit, instead of only sending a warning email. The $5 of credit already caps spending; this limit still protects you if you ever buy more credit or turn auto-reload on by mistake. See Step E.

OpenAI API key (SECRET). This key is the password the create-task-with-ai function presents to OpenAI when it asks for a label. It is shown only once, at creation. It goes to Supabase as a secret — never in .env.local, never in browser code — because anyone holding it can spend your credit. See Step E.

Stripe (payments, test mode only: no real money)

Email you use to sign in to Stripe. This only records which account owns the test-mode store. See Step F.

Publishable key (test mode). Stripe’s publishable key is made to be seen in web pages: it identifies your account to Stripe’s card form. This app does not use it anywhere, because it sends users to Stripe’s own checkout page instead of showing a card form itself. Record it anyway: it belongs with the account’s keys, and you would need it if the app ever showed the payment form inside its own pages. See Step F and Publishable and Secret Keys.

Secret key (test mode) (SECRET). This key can do anything in your Stripe account, so it only ever goes to servers. In this app it lives in two server places: as a Supabase secret, where the Edge Functions read it to create checkout pages and open the customer portal; and in Supabase Vault, where the database reads it to create a Stripe customer record for each new user. The automated tests read it from .env.test.local. See Step F and Publishable and Secret Keys.

Product name. A product is what you sell — here, the Premium subscription. The name shows on the checkout page, so the buyer sees what they are paying for. See Step F.

Price ID of the monthly price. A price says how much and how often: one product can have several prices. When a user upgrades, the app asks Stripe for a subscription to one price, by its ID — which is why the app needs the price ID, not the product’s ID. A price ID is not secret, but it stays on the server as a Supabase secret so that nobody in the browser can change which price is charged. See Step F.

Webhook signing secret (SECRET). Stripe signs every webhook message with this secret, and the stripe-webhook function checks the signature before believing the message. Without that check, anyone could send a fake “payment succeeded” message and get Premium for nothing. The secret belongs to one webhook endpoint, so it is created when you create the endpoint, and it goes to Supabase as a secret. See Step H.

Vercel (putting the app online, at the end)

How you sign in to Vercel. Signing in with GitHub connects Vercel to your repositories, so Vercel can import the task-app repo and deploy a new version every time you push. See Step K.

Your app’s address on Vercel. The public address of the deployed app, given by Vercel after the first deployment. Supabase and Google must both learn it: Supabase’s Site URL and redirect list, and Google’s authorized origins, only send users back to addresses they list. See Step K.

The commands, in worksheet order

The worksheet’s Commands sheet builds the exact lines you copy: the settings-file lines, the terminal commands, one SQL line, and the addresses you paste into websites. A line shows “(fill in … first)” until the values it needs are on My Info. Below, ... stands for your value: copy the real line from the worksheet, never from this page. Every terminal command runs from inside the task-app folder — start with the cd line — because npx runs the Supabase CLI from that folder’s installed packages. See Step C.

1. Copy your fork to your computer

git clone https://github.com/YOUR-USERNAME/task-app

Clone means: download a copy of the repository, including its history, and remember where it came from — so later git push knows where to upload. The copy lands in a new task-app folder. See Step B.

2. The file task-app/.env.local

.env.local is a settings file on your computer. Settings differ for every student, so they cannot be written into the shared code. The app reads them when it starts, and Git never uploads the file: the project’s .gitignore excludes it. You create it by copying the template .env.example (which holds only fake values, safe to share), then replace the two lines with the worksheet’s lines. See Step C and Step 3: Storing your private info (env files, etc).

NEXT_PUBLIC_SUPABASE_URL="..."
NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY="..."

Line 1 tells the app where its back end lives. Line 2 is the key the browser code presents with its requests. Both names start with NEXT_PUBLIC_, which tells Next.js to build the values into the web pages every visitor’s browser downloads. That is right for these two values — the address and the publishable key are meant to be public — and it is why a secret key must never get a NEXT_PUBLIC_ name. See APIs, API Keys, and Third-Party Services.

3. Terminal commands for the app

cd ~/projects/full-stack-demo-app/task-app

Each new terminal starts in full-stack-demo-app, one folder above the code. This line moves into task-app first, so the commands that follow find the project. It is harmless if you are already there; it just makes sure.

npx supabase login

This proves to Supabase who you are: it opens your browser, you sign in, and the CLI keeps a login token on your computer, so the commands that follow act on your account without asking again. See Step C.

npx supabase link --project-ref ...

This records which Supabase project this folder belongs to. Later commands — pushing the database, setting secrets, deploying functions — then go to your project without you naming it each time. Supabase may ask for the database password here, because linking connects to the project itself. See Step C.

npx supabase db push

This applies the project’s migrations: the files in supabase/migrations that create the tables (profiles, tasks, usage tracking), the security rules, the task-attachments storage bucket for images, and the Stripe connection. “Push” means upload: the files describe the database, and this command makes the hosted database match them. See Step G.

npx supabase secrets set OPENAI_API_KEY=...
npx supabase secrets set STRIPE_SECRET_KEY=...
npx supabase secrets set STRIPE_PRICE_ID=...
npx supabase secrets set STRIPE_WEBHOOK_SECRET=...

Each line stores one named secret on Supabase’s servers. The Edge Functions read secrets by name when they run; the values never appear in the code or on GitHub. There is one line per value the functions need: the OpenAI key for labels, the Stripe secret key and price ID for checkout, and the webhook signing secret for checking Stripe’s messages. Note that the Supabase secret key has no line here: Supabase hands it to the functions by itself. A secret you set is available to the deployed functions without redeploying them. See Step E, Step F, and Step H.

npx supabase functions deploy create-task-with-ai
npx supabase functions deploy create-stripe-session
npx supabase functions deploy stripe-webhook --no-verify-jwt

Each line uploads one Edge Function — a small program that runs on Supabase’s servers, waits to be called, does one job, and stops — named by its folder in supabase/functions. create-task-with-ai saves a new task and asks OpenAI for its label. create-stripe-session checks the user’s login and asks Stripe for a checkout page at your price. stripe-webhook receives Stripe’s payment messages. The last line carries --no-verify-jwt: normally Supabase checks every call for a valid user login token before the function runs, but Stripe has no login token, so the check is turned off for this function — and the function checks Stripe’s signature instead. See Step H and Project Architecture.

4. One SQL line, in the Supabase SQL Editor

select vault.create_secret('...', 'stripe');

This stores the Stripe secret key a second time, in Supabase Vault: an encrypted store for secrets inside your database. The Edge Functions read the key from their secrets; the database reads it from Vault to create a Stripe customer record for each new user. That is also why Step C says not to sign in to the app before Step F is finished: creating a user triggers the Stripe-customer step, which needs the Vault key. After running the line, discard the editor text, so the line with your key is not kept in Supabase’s list of saved queries. See Step F.

5. Addresses you paste into websites

These five paste-ins are all allow lists: each service only sends users (or messages) to addresses it has been told in advance, so nobody can redirect a freshly signed-in user — with their login token — to a different website.

  • Google Cloud, Authorized JavaScript origins (local): http://localhost:3000. The web address your app runs at while you develop it. Google lists the origins that may start a sign-in. See Step D.
  • Google Cloud, Authorized redirect URIs: the Google callback URL from the worksheet. After Google signs the user in, it sends the browser here — to Supabase, not to your app — with a one-time code. Google refuses any redirect URI that is not listed, exactly. See Step D.
  • Supabase, Site URL (while you work locally): http://localhost:3000. The default address Supabase sends the user back to after sign-in. See Step C.
  • Supabase, Redirect URLs (local): http://localhost:3000/**. The allow list of return addresses. The app returns to addresses under the home page (such as /dashboard), so the entry ends in **, which matches any characters including /. See Step C.
  • Stripe, webhook endpoint URL: the Stripe webhook URL from the worksheet. This tells Stripe where to send payment messages. See Step H.

6. After you deploy to Vercel

Vercel builds the app from your GitHub fork and serves it at a public address. Two things must follow the move: the app’s settings, and the allow lists.

NEXT_PUBLIC_SUPABASE_URL=...
NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY=...

These are the same two values as in .env.local, entered as Vercel environment variables. .env.local is never uploaded to GitHub, so Vercel cannot see it: the values must be entered again on Vercel. Only these two go here — the secret keys live on Supabase, not in Vercel. Without the URL, the build fails: the pages are built with these values baked in, and with no back-end address there is nothing to build against. If you add or change a variable later, redeploy: a change applies only to new deployments, because the values are baked in at build time. See Step K.

Then update the three allow lists with the Vercel address, keeping the localhost entries for local work: Supabase Site URL becomes the Vercel address; add a redirect URL for the Vercel address ending in /**; add the Vercel address to Google’s authorized JavaScript origins. The redirect URI stays the Supabase callback URL, and Stripe needs no changes, because the webhook address belongs to your Supabase project and does not move. Every git push to your fork makes Vercel deploy the new version automatically. See Step K.

7. Optional: task-app/.env.test.local for the automated tests

NEXT_PUBLIC_SUPABASE_URL="..."
NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY="..."
SUPABASE_SECRET_KEY="..."
STRIPE_SECRET_KEY="..."
STRIPE_PRICE_ID="..."
STRIPE_WEBHOOK_SECRET="..."

The automated tests are programs that sign up test users, create tasks, and check the subscription logic against your real Supabase project. They need the same values the app and the functions use, plus the Supabase secret key — under the name SUPABASE_SECRET_KEY, without NEXT_PUBLIC_ — so they can set up and check test data with the security rules out of the way. Like .env.local, this file is ignored by Git and must never be committed. See Step L.

Other commands from the step pages (not on the worksheet)

cp .env.example .env.local

Copies the settings template, with fake values, to the real settings file. See Step C.

npm install

Reads package.json, the app’s list of the packages it needs, and downloads them into node_modules. Run it once after cloning, and again whenever package.json changes. See Step B.

npm run dev

Starts the development server: a web server on your own computer, at http://localhost:3000, that hands the app’s pages to your browser and reloads them when the code changes. Stop it with Ctrl+C. See Step C and Step I.

git status
git add -A
git commit -m "Set up the task app"
git push

git status lists what changed and changes nothing — check that .env.local is not in the list. git add -A stages every change. git commit saves a snapshot in the project’s history. git push uploads the new commits to your fork, which also makes Vercel deploy the new version. See Step J.

npm test

Runs the automated tests with the testing tool Jest. See Step L.

Why every service gives you two keys

The same shape repeats at Supabase, Stripe, and Google: one value that may be seen, and one that must stay secret. The public value identifies your app or project and unlocks only safe, limited powers — reading through the security rules, showing a card form, starting a sign-in. The secret value proves your app’s identity to the service and unlocks the real powers — bypassing the security rules, charging cards, finishing a sign-in. Two values with different powers let the browser carry the safe one while the servers keep the powerful one.

That is why each worksheet row says which side the value belongs to. Whenever you are unsure where a value goes, ask one question: would an attacker gain anything by reading it in a web page? If yes, it belongs on a server — as a Supabase secret, in the Vault, or in Supabase’s dashboard settings — and never in .env.local under a NEXT_PUBLIC_ name, never in Vercel, and never in Git. If a key ever leaks, delete it and make a new one: deleting a leaked key from a file does not undo the leak, because anyone who copied it still has it. See Publishable and Secret Keys and APIs, API Keys, and Third-Party Services.

Deeper dive: public keys, private keys, and the keys on this page

A real public/private key pair is two mathematically linked halves. What the private half signs, only the public half can verify — and the public half can never be used to work out the private half. One way to picture it is a padlock: anyone can snap a padlock shut, but only the person with the key can open it. The public half is the padlock; the private half is the key.

The publishable and secret keys on this page are not such a pair. They are two independent passwords with different powers: each is a random string the service looks up in its own records, and either can be replaced without touching the other. Do not call them a key pair.

One real key pair does work behind the scenes here: Supabase signs each user’s login token with a private signing key, and publishes the matching public key so any service can check the signature and trust the token — without ever being able to make a token of its own.

The webhook signing secret is a third kind: a shared secret. Stripe and your app both hold the same secret. Stripe uses it to sign each message; your function uses it to check the signature and know the message really came from Stripe. See Publishable and Secret Keys.

Key takeaways

  • The browser shows pages; Vercel serves them; Supabase holds the data, the logins, the storage, and the Edge Functions; Google, OpenAI, and Stripe each do one job.
  • Everyday data goes browser to Supabase directly, under Row Level Security. Jobs that need a secret key go through an Edge Function. Stripe calls the webhook function back with payment news.
  • Every worksheet value has exactly one home: a file, a dashboard, a secret store, or the Vault. A secret that ends up in the wrong home is either useless there or dangerous there.
  • The setup order is also a dependency order: the project and its keys come before the functions that use them, and the Vault key comes before the first user signs up.

Practice Questions

Easy

Question 1 · Multiple choice

A signed-in user opens the app and sees their own tasks. Which path did that request take?

  1. The browser asked Stripe, and Stripe returned the tasks.
  2. The browser asked the Supabase Data API, with the publishable key and the user’s login token.
  3. The browser asked an Edge Function, which read the tasks with the secret key.
  4. The browser asked Vercel’s build server, which returned the tasks from GitHub.
Suggested answer
  1. The browser asked the Supabase Data API, with the publishable key and the user’s login token. Everyday data reads and writes go directly from the browser to Supabase, and the Row Level Security rules decide which rows that user may see. Edge Functions are only for jobs that need a secret key; Stripe and Vercel hold no task data.

Question 2 · Short answer

What two values go in .env.local, and why do their variable names start with NEXT_PUBLIC_?

Suggested answer

The Project URL (NEXT_PUBLIC_SUPABASE_URL) and the publishable key (NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY). The NEXT_PUBLIC_ prefix tells Next.js to build the values into the web pages that every visitor’s browser downloads. That is right for these two values, because the back end’s address and the publishable key are meant to be public.

Question 3 · True or false

The Stripe secret key may go in .env.local, because the app uses Stripe in test mode and no real money is involved.

Suggested answer

False. The Stripe secret key can do anything in the Stripe account, even in test mode, and it must only ever go to servers: as a Supabase secret for the Edge Functions, and in Supabase Vault for the database. Test mode protects real money; it does not make a secret key safe to put in a file or a web page.

Question 4 · Short answer

What do Row Level Security (RLS) rules decide?

Suggested answer

Which rows each user may see and change. The rules run in the database itself, so even a request that skips the app’s pages — a direct API call with the publishable key — only reaches the rows the rules allow for that user.

Question 5 · Short answer

What is the project ref, and name two addresses the worksheet builds from it.

Suggested answer

The project ref is the project’s unique ID: 20 letters. The worksheet builds four addresses from it, any two of which answer the question: the Project URL (https://<ref>.supabase.co), the Google callback URL, the Stripe webhook URL, and the project dashboard URL.

Medium

Question 6 · Ordering

Put these steps of a Google sign-in in order, from first to last.

  1. Google sends the browser back to Supabase’s callback address with a one-time code.
  2. The user signs in on Google’s page.
  3. Supabase sends the user to Google’s sign-in page.
  4. Supabase exchanges the code for the user’s name and email, presenting the Client secret.
  5. Supabase sends the browser back to the app.
Suggested answer

The order is c, b, a, d, e. Supabase sends the user to Google’s sign-in page (c); the user signs in on Google’s page (b); Google sends the browser back to Supabase’s callback address with a one-time code (a); Supabase exchanges the code for the user’s name and email, presenting the Client secret (d); Supabase sends the browser back to the app (e).

Question 7 · Scenario

Maria adds STRIPE_SECRET_KEY to her .env.local, but never runs npx supabase secrets set. She clicks Upgrade in the app. What goes wrong, and why?

Suggested answer

The checkout fails. The Edge Function create-stripe-session runs on Supabase’s servers and reads its secrets by name from Supabase — it does not read .env.local, which only exists on Maria’s computer. With no secret set, the function has no Stripe key to ask Stripe for a checkout page. The fix is to run the secrets set line with the key, and to remove the key from .env.local, where it does no good.

Question 8 · Multiple choice

Why is stripe-webhook deployed with --no-verify-jwt?

  1. Webhook functions run faster without the login check.
  2. Stripe calls the function without a Supabase login token, so the login check would reject every message; the function checks Stripe’s signature instead.
  3. The webhook function has no login to check, because it never touches the database.
  4. The flag tells Supabase to skip checking the webhook signing secret.
Suggested answer
  1. Stripe calls the function without a Supabase login token, so the login check would reject every message; the function checks Stripe’s signature instead. Normally Supabase checks every Edge Function call for a valid user login token before the function runs. The webhook turns that check off and replaces it with the signature check, using the webhook signing secret.

Question 9 · Short answer

The app’s code never uses the Stripe publishable key. Why does the worksheet still have a row for it?

Suggested answer

The row keeps the account’s keys recorded together, and the key would be needed if the app ever showed Stripe’s payment form inside its own pages. This app sends users to Stripe’s own checkout page instead, so the browser never needs the publishable key. The key is safe to record because it is made to be seen.

Question 10 · Matching

Match each secret to where it lives in this project.

Secrets: (1) OpenAI API key, (2) Stripe secret key, (3) webhook signing secret, (4) Supabase secret key, (5) Google OAuth Client secret.

Homes: (a) a Supabase secret, read by the Edge Functions, (b) Supabase Vault and a Supabase secret, (c) .env.test.local only, for the automated tests, (d) Supabase’s Google provider settings.

Suggested answer
  1. → (a): the OpenAI API key is a Supabase secret, read by create-task-with-ai. (2) → (b): the Stripe secret key lives in Supabase Vault for the database and as a Supabase secret for the Edge Functions. (3) → (a): the webhook signing secret is a Supabase secret, read by stripe-webhook. (4) → (c): the Supabase secret key’s only manual home is .env.test.local; Supabase hands it to the Edge Functions by itself. (5) → (d): the Google Client secret lives in Supabase’s Google provider settings.

Hard

Question 11 · Scenario

Sam clicks Upgrade, pays with the test card, and sees the payment in his Stripe dashboard — but the app still shows the free plan. Name two places to look, and say what each would tell you.

Suggested answer

First, the stripe-webhook function’s logs in the Supabase dashboard: they show whether the function received Stripe’s message and what it did with it — for example, a signature check that failed. Second, the webhook endpoint in the Stripe dashboard: it shows whether Stripe sent the event and whether the endpoint answered. The webhook function always answers OK even when it rejects a message, so a “delivered” event in Stripe does not prove the user was upgraded — the function logs are what show the rejection.

Question 12 · Compare

Supabase gives you a publishable key and a secret key. Explain why these are NOT a public/private key pair, and name one place in this stack where a real key pair IS used.

Suggested answer

A real key pair is two mathematically linked halves: what the private half signs, only the public half can verify, and the public half can never reveal the private half. Supabase’s publishable and secret keys are two independent random strings, each looked up in Supabase’s own records, with different powers — either can be replaced without touching the other. A real key pair IS used behind the scenes for login tokens: Supabase signs each token with a private signing key and publishes the matching public key so services can verify the token without being able to make one.

Question 13 · Scenario

The class moves the app from localhost to Vercel. List everything that must change for the deployed app to work, and say why each change is needed. Also name two things that do NOT change, and why.

Suggested answer

What must change: (1) The two NEXT_PUBLIC_ values must be entered as Vercel environment variables, because .env.local is never uploaded to GitHub and Vercel cannot see it; without the URL, the build fails. (2) Supabase’s Site URL must become the Vercel address, so users are sent back to the deployed app after sign-in. (3) A redirect URL for the Vercel address must be added, so Supabase allows the return address. (4) The Vercel address must be added to Google’s authorized JavaScript origins, so Google allows sign-ins that start from it. What does not change: the Google redirect URI stays the Supabase callback URL, because Google always answers to Supabase; and the Stripe webhook endpoint stays as it is, because its address belongs to the Supabase project and does not move when the front end moves.

Question 14 · Scenario

A student commits .env.test.local to GitHub by accident. What must they do, in order, and why is deleting the commit not enough?

Suggested answer

First, treat every value in the file as leaked: revoke the Supabase secret key and the Stripe secret key, delete the webhook endpoint’s signing secret, and make new ones — then update the worksheet, the Supabase secrets, the Vault, and .env.test.local with the new values. Second, remove the file from Git and check that .gitignore still excludes it. Deleting the commit is not enough because the file may already have been copied — automated scanners watch public repositories for keys — and a deleted commit stays in the repository’s history and in any copy anyone took. Only new keys make the leaked ones useless.

Question 15 · Short answer

A price ID is not secret: Stripe shows it in the dashboard. Why does it still live on the server as a Supabase secret, instead of in the browser code?

Suggested answer

Because the server, not the browser, must decide what is sold at what price. If the price ID lived in the browser code, a user could change it and ask Stripe for a different price — for example, a cheaper one. Keeping it as a secret means only the Edge Function chooses the price, and the browser only asks to upgrade.
