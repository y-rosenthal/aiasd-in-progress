Lecture 5: Extending Claude Code: Subagents, Hooks, Plugins, and Mods

Live demo script for this class

Date: to be announced

Topic: Out of the box, Claude Code reads files, edits them and runs commands. Extensions add to that: helpers with their own context (subagents), commands that run automatically (hooks), packages that other people built (plugins), and code that changes Claude Code itself (mods). Today we learn what each one is for, when it is worth adding to your final project, what it costs, and why you must read an extension before you trust it.

How to use this page. Each section below is one part of the class. It starts with the chapter section to open, then lists the key points, then points to the matching part of the live demo script. Links open in a new tab. After class, use this page to review: the chapters have the full explanations and more practice questions.

1. Why this matters now

  • Your team builds its final-project app with Claude Code. Every member must explain the whole project in the oral exam, including how the team set up Claude Code.
  • A few extensions help a team a lot:
    • a helper that reviews each change for bugs and leaked keys before a pull request;
    • a helper that explores the code and explains how it works (good practice for the oral exam);
    • a rule that Claude Code enforces, such as “never edit .env.local”, instead of a rule that Claude only reads.
  • Two warnings come with them:
    • Every extension costs something: room in Claude’s context window, and part of your plan’s usage.
    • Many extensions run code on your computer, as you. Read them before you install them.

2. The map, and what each extension costs

Open: Extending Claude Code: The Big Picture › The extension points at a glance

As of Nov 24, 2026 · Official docs: Extend Claude Code

  • The extensions, with a final-project example of each:

    Extension What it is Final-project example
    CLAUDE.md Instructions loaded in every session The team’s Git rules from the last class
    Skill Instructions for one kind of task, loaded when needed A checklist for adding a new page to the app
    MCP server A connection to an outside service, with new tools The Supabase MCP server (Hands-On: The Supabase MCP Server)
    Subagent A helper with its own context window that returns a summary A code reviewer; a repository explorer
    Hook Your command, run by Claude Code at a certain moment, every time Block edits to .env.local; a notice when Claude needs you
    Plugin A package of skills, subagents, hooks, MCP servers and more commit-commands from Anthropic’s official marketplace
    Mod A plugin with code that runs inside Claude Code and changes how it looks and behaves Not needed for the project

  • Guidance or guarantee? CLAUDE.md, skills and output styles are guidance: Claude reads them and usually follows them. Hooks and permission rules are enforced by Claude Code, whatever Claude decides (Which one should I use?).

  • Add an extension when you need it, not all at once. For example: Claude gets a project rule wrong twice, so add a line to CLAUDE.md. A side task fills your conversation with output, so use a subagent.

  • Every extension costs some context (Every extension costs some context):

    • CLAUDE.md is in every request.
    • Skills and MCP servers put their names and short descriptions in every request; the full text loads only when used.
    • A subagent works in its own context window; only its summary comes back.
    • A hook costs nothing in the context unless it returns output.

  • Type /context in a session to see what uses the space (Context, Models, Effort, and Usage). Remove what you don’t use.

3. Subagents

Open: Subagents › What a subagent is

As of Nov 24, 2026 · Official docs: Create custom subagents

  • A subagent is a separate AI assistant that Claude starts for one task. It has its own context window, its own instructions and its own allowed tools. When it finishes, only its summary comes back to your conversation.

  • Claude Code has built-in subagents. Explore searches and reads the code without changing it. Claude uses them by itself, or when you ask:

    Use a subagent to explore this repository and explain how a payment goes from the checkout button to Stripe

  • Your own subagent is a Markdown file in .claude/agents/ (Creating your own subagent). Commit it, and every teammate gets it. The frontmatter at the top sets:

    • name and description (required). The description tells Claude when to use it.
    • tools: what it may use. A reviewer gets Read, Grep, Glob, Bash, but not Edit or Write.
    • model: for example inherit (the same model as your conversation) or haiku (faster and cheaper).

  • To make sure that your subagent runs, @-mention it: @"code-reviewer (agent)" review my changes.

  • A subagent starts fresh. It doesn’t see your chat. If you told Claude “ignore the vendor/ folder” only in the chat, ask Claude to include that in the task, or put it in CLAUDE.md.

  • Subagents are not free. Each one sends its own requests to the model, which count toward your plan’s usage limits.

4. Hooks

Open: Hooks › Block edits to .env files

As of Nov 24, 2026 · Official docs: Automate actions with hooks · Hooks reference

  • A hook is your own command that Claude Code runs automatically at a hook event, such as PreToolUse (before Claude uses a tool) or Notification (Claude Code needs your attention). It runs every time; the AI model doesn’t decide.

  • A hook has three levels in a settings file (How a hook is configured):

    "hooks"
 └── event, e.g. "PreToolUse"                 WHEN should it run?
      └── "matcher": "Edit|Write"             WHICH tool calls?
           └── "hooks": [ { "type": "command", "command": "..." } ]   WHAT runs?

  • Block edits to secret files. A PreToolUse hook runs a script before every Edit or Write. If the file is .env, .env.local or similar, the script exits with code 2, and Claude Code cancels the edit.

  • Only exit code 2 blocks (How a hook blocks an action). Exit code 1 is an error, and the edit goes ahead. A script that can’t find jq can end with exit code 0 and block nothing. Test the script by hand before you trust it.

  • The hook sees only the tools that it matches. Claude can still change .env.local with a shell command. A permission deny rule such as Edit(/.env.local) adds a second layer (Allow and deny rules).

  • Get a notice when Claude needs you. A Notification hook shows a desktop notice when a permission prompt waits, or when Claude finished about 60 seconds ago and you haven’t typed (Get notified when Claude needs you).

  • Where to put a hook: .claude/settings.json for the whole team (commit it), .claude/settings.local.json for you in this project, and ~/.claude/settings.json for you in every project. Type /hooks to see the hooks that are active and where each comes from.

Demo: Part B: block edits to .env files and Part C: a notice when Claude needs you.

5. Plugins and marketplaces

Open: Plugins and Marketplaces › Installing and managing plugins

As of Nov 24, 2026 · Official docs: Install and manage plugins · Plugin security and trust

  • A plugin packages skills, subagents, hooks, MCP servers and more, so that you install them with one command. A marketplace is a catalog of plugins. Claude Code adds Anthropic’s official marketplace, claude-plugins-official, the first time you start an interactive session.
  • /plugin opens the plugin panel: Discover, Installed, Marketplaces and Errors tabs.
  • /plugin install commit-commands@claude-plugins-official doesn’t install right away. It shows the plugin’s details first:
    • Will install: the skills, agents, hooks and MCP servers it adds;
    • Context cost: the tokens it adds to every message, and when it is used (shown for plugins in the official marketplace).
  • Then you pick a scope: you in every project (user), the whole team (project), or you in this project only (local).
  • Read it before you install it. Open the plugin’s source on GitHub (View on GitHub in the details). commit-commands has three Markdown command files and nothing else. Its commit command lists allowed-tools: Bash(git add:*), Bash(git status:*), Bash(git commit:*): while it runs, Claude may run those git commands without asking you. Check for hooks (hooks/hooks.json), MCP servers (.mcp.json) and programs (bin/) too.
  • An enabled plugin is part of every session: its skill and agent descriptions use context, and its MCP servers run as programs on your computer. Disable the plugins you don’t use, especially on a slow laptop (What an enabled plugin costs).

Demo: Part D: read, install and use a plugin.

6. Mods, in ten minutes

Open: Mods › What a mod is

As of Nov 24, 2026 · Official docs: Mods overview

  • A mod is a plugin with JavaScript or TypeScript code that runs inside Claude Code. It can draw a pane beside the conversation, add a /command that runs at once, or step into a tool call.
  • You already use mods: some Claude Code features are built-in mods, for example the pane of /diff (Mods you already have).
  • You don’t need a mod for the final project. A hook, a skill or a subagent is simpler for what you need.
  • Mods aren’t sandboxed. A mod runs with your permissions. On a personal setup it can approve tool calls that your ask rules or hooks would stop (Safety: mods are not sandboxed).
  • Before you load a mod, run claude plugin validate <folder>. Its hooks: line lists the events the mod handles; its calls: line lists what it asks Claude Code to do, such as read files or make network requests.
  • To turn mods off: disable one in /plugin, start one session with claude --safe-mode, or add "disableAllHooks": true to your settings (this stops your settings hooks too).

Demo: Part E: the built-in mods, and checking a sample mod.

7. Trust and security

Open: Plugins and Marketplaces › Trust and security

As of Nov 24, 2026 · Official docs: Plugin security and trust · Hooks reference: Security considerations

  • The official docs say it directly:
    • “Command hooks execute shell commands with your full user permissions.”
    • “A Claude Code plugin you install can execute arbitrary code on your machine with your user privileges.”
    • “A mod is code that runs with your permissions.”
  • Your permission rules and the sandbox cover the tool calls Claude makes. They don’t cover the hooks, MCP servers and mod code that a plugin runs by itself.
  • Skills and subagent files are instructions. They change what Claude does, so text from a stranger can steer Claude (Prompt injection and untrusted content).
  • A cloned repository can contain hooks in its .claude/settings.json. In an interactive session, Claude Code holds them back until you accept the workspace trust prompt for the folder. claude -p doesn’t ask, so the hooks run at once (Hooks and safety).
  • In your team: review a teammate’s changes to .claude/ in a pull request as carefully as code. A new hook is a new program that runs on your laptop.
  • A short checklist before you add any extension:
    1. Who wrote it? Where does it come from?
    2. Read every file that runs code: hook scripts, hooks/hooks.json, .mcp.json, bin/, and mod code (claude plugin validate).
    3. Don’t understand it? Don’t install it.
    4. Choose the narrowest scope, and disable it when you stop using it.

8. What to add to your final project

A small setup is enough. Do it in one pull request, so the team reviews it:

  1. CLAUDE.md with the team’s Git rules (from the last class).
  2. A code-reviewer subagent in .claude/agents/code-reviewer.md (committed). Run it before every pull request; a teammate still reviews the PR.
  3. The .env guard hook in .claude/settings.json and .claude/hooks/protect-files.sh (committed), plus deny rules for .env.local. Every teammate tests the script once by hand.
  4. Personal settings stay personal: the notification hook goes in your own .claude/settings.local.json or ~/.claude/settings.json, not in the committed file.
  5. Plugins: at most one or two that the team read and agreed on. No mods.
  6. The oral exam: every member can explain what each file in .claude/ does, and why the team added it.

Key takeaways

  • Each extension has a job: subagents keep side tasks out of your context, hooks enforce rules every time, plugins package and share setups, and mods change Claude Code itself.
  • Every extension costs some context or usage. Add one when you need it, check with /context, and remove what you don’t use.
  • Only hooks and permission rules are enforced; CLAUDE.md and skills are guidance. In a PreToolUse hook, only exit code 2 blocks.
  • Hooks, plugins and mods run code with your permissions. Read them before you install them, and review changes to .claude/ like code.

Practice Questions

More questions on each topic are at the end of each chapter linked above.

Easy

Question 1 · Matching

Match each need with the extension that fits best.

Need Extension
1. Claude must never edit .env.local, without exceptions A. Subagent
2. Read 40 files and get back only a short explanation B. Plugin
3. Install a set of commit commands that someone else built C. Hook
4. A pane with buttons inside Claude Code’s screen D. Mod
Suggested answer

1 → C, 2 → A, 3 → B, 4 → D. A hook is enforced every time; a subagent keeps the reading in its own context and returns a summary; a plugin packages work that others built; only a mod can draw in Claude Code’s interface.

Question 2 · True or false

“A subagent can see everything you said to Claude earlier in the chat.”

Suggested answer

False. A normal subagent starts with a fresh context: its own instructions, the task that Claude writes for it, and your CLAUDE.md files (the built-in Explore and Plan subagents skip CLAUDE.md). It doesn’t see the chat. Put lasting rules in CLAUDE.md, or ask Claude to include them in the task.

Question 3 · Multiple choice

A PreToolUse guard script finds that Claude wants to edit .env.local. With which exit code must it end to block the edit?

  1. 0
  2. 1
  3. 2
  4. Any code other than 0
Suggested answer

c. Only exit code 2 blocks. Exit code 0 means “no objection” (a), and any other code, such as 1, is a non-blocking error: the edit goes ahead (b, d).

Medium

Question 4 · Short answer

Your team installed five plugins at the start of the project but uses only one. Why does this matter even if nobody runs the other four?

Suggested answer

An enabled plugin is part of every session. The names and descriptions of its skills and agents use context in every request, its MCP servers run as programs alongside each session, and its hooks fire at their events. This costs usage and context and slows a weak laptop. Disable or uninstall the four plugins you don’t use.

Question 5 · Read the file

Read this subagent file. (a) When will Claude use it? (b) Can it change files with the Edit tool? (c) Can it change files in some other way?

---
name: code-reviewer
description: Reviews code changes for bugs and leaked secrets. Use after code is written or changed.
tools: Read, Grep, Glob, Bash
model: inherit
---

Run git diff, read the changed files, and report problems by priority.
Suggested answer
  1. When a request matches its description (after code is written or changed), or when you @-mention it or ask for it by name. (b) No: Edit is not in its tools list. (c) Yes, in principle: it has Bash, and shell commands can change files. Those commands still go through Claude Code’s permission checks and your deny rules. It needs Bash to run git diff.

Question 6 · Scenario

Sam wants a desktop notice when Claude needs him. Maria doesn’t want one. Where should Sam put the Notification hook, and why not in the committed .claude/settings.json?

Suggested answer

In his own settings: .claude/settings.local.json (just him, in this project) or ~/.claude/settings.json (just him, in every project). The committed .claude/settings.json applies to everyone who works in the repository, so Maria would get the notices too. (Also, the notice command differs between Mac, Windows and Linux.)

Hard

Question 7 · Find the bug

Maria added the .env guard hook. When she tests it by hand, she sees this. Explain why the guard doesn’t work and how to fix it.

$ echo '{"tool_name":"Edit","tool_input":{"file_path":".env.local"}}' | .claude/hooks/protect-files.sh
.claude/hooks/protect-files.sh: line 5: jq: command not found
$ echo $?
0
Suggested answer

jq isn’t installed, so the script can’t read the file path. The path is empty, matches no pattern, and the script reaches exit 0, which means “no objection”: every edit goes ahead. Fix: install jq (for example brew install jq on a Mac, or winget install jqlang.jq on Windows), then repeat the test until echo $? prints 2. A deny rule such as Edit(/.env.local) is a useful second layer.

Question 8 · Long answer

A classmate’s repository has a .claude/settings.json with hooks. Explain why running claude -p "summarize this project" in it can be risky, and what you should do first.

Suggested answer

Hooks run shell commands with your full user permissions. In an interactive session, Claude Code holds back the folder’s hooks until you accept the workspace trust prompt. claude -p never shows that prompt and treats the folder as trusted, so the repository’s hooks run at once. First read the repository’s .claude/ settings files and hook scripts, or turn hooks off for that run with --settings '{"disableAllHooks": true}'.

Question 9 · Long answer

Before installing a plugin from a third-party marketplace, what do you check, and why don’t your permission deny rules protect you from a bad plugin?

Suggested answer

Check who publishes the marketplace and the plugin; read the Will install list in /plugin; open the source and read hooks/hooks.json (what each hook runs), .mcp.json (each server’s command or address), everything in bin/, any mod code (claude plugin validate), and the skills’ allowed-tools. If you don’t understand it or don’t trust the author, don’t install it.

Deny rules and the sandbox cover the tool calls that Claude makes. A plugin’s hooks, MCP servers and mod code are run by Claude Code itself, with your permissions and outside the sandbox, so a deny rule doesn’t stop them.
