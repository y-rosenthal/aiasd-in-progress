90  90. Project 3: Build Your Own App

Draft: not yet approved

This page is a draft for the instructor. The milestones, dates, deliverables and grading may change before the project is assigned.

In this final project you build a web app for your own business idea, from scratch, with Claude Code as your partner. You use the same architecture as the task app from Classes 10–12: Next.js, Supabase, GitHub and Vercel. In Project 2: Change the Task App’s Database you changed an app that already existed; now you design one yourself.

90.1 Goals

By the end, you will have turned a business idea into a short written spec, designed a small database with rules that keep each user’s data private, built and tested the app on your computer, put it online, and directed an AI coding agent through a real project while checking its work. The point is a small app that works, that you understand and can explain.

90.2 Choose and scope your idea

Pick a problem that a real small business, club or freelancer has. Then cut it down until it fits in a few weeks. A good project has:

  • one main workflow: the one thing a user comes to the app to do, from start to finish;
  • 2-3 tables of your own in the database (the user accounts come with Supabase);
  • one kind of user, who signs in and sees only their own data.

Some ideas that fit:

Idea Tables Main workflow
Booking for a hair salon services, appointments A customer picks a service and a time, and sees their upcoming appointments
Invoice tracker for a freelancer clients, invoices Add a client, create an invoice, mark it paid, see what’s still owed
Inventory for a small café items, stock_counts Record today’s count of each item, and see which items are running low
Resale tracker for a thrift seller items, sales Add an item with its cost, record the sale, see the profit per month
Dues for a student club members, payments Add members, record who paid, list who still owes dues

Signs that an idea is too big: two kinds of users (buyers and sellers), chat, maps, a phone app, real money, or several outside services. Keep those for “version 2” in your spec.

Start smaller than you think

Your first version is your MVP (minimum viable product): the smallest app that does the main workflow. Get it working and online first. Add extras only after that. See Putting It Together: Architecting a Web App with AI.

90.3 The starter template

As of Oct 16, 2026 · Official docs: Use Supabase with Next.js · The with-supabase example

You don’t start from an empty folder. Supabase and Next.js publish an official starter template: a small, working Next.js app that is already connected to Supabase, with sign-up, login and password-reset pages (email and password). Supabase’s guide creates it with:

npx create-next-app@latest my-app -e with-supabase
  • npx create-next-app@latest downloads and runs the newest version of Next.js’s app creator.
  • my-app is the name of the new folder for your app’s code. Use your app’s name, in lowercase with dashes, for example salon-booking.
  • -e with-supabase means “start from the example named with-supabase”.

The command also makes the folder a Git repository, with a first commit. The app needs two settings, which go in a file named .env.local: NEXT_PUBLIC_SUPABASE_URL (your project’s URL) and NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY (your project’s publishable key). The template’s .gitignore already keeps .env.local out of Git. (Older guides call the key ..._ANON_KEY; see Environment Variables and .gitignore and Keeping Secrets Out of Git.)

Claude runs these commands for you, after asking your permission. The template changes over time, so the prompt below tells Claude to check Supabase’s guide first.

Deeper dive: Why every NEXT_PUBLIC_ value is public

Next.js copies the value of every variable whose name starts with NEXT_PUBLIC_ into the JavaScript that it sends to the browser. Anyone can read it there. That is fine for the Supabase URL and the publishable key, because Row Level Security decides what that key may do. A secret key, such as an OpenAI or Stripe key, must never go in a NEXT_PUBLIC_ variable. It belongs only on a server: in a Supabase Edge Function’s secrets, as the task app does, or in a Vercel variable without the prefix. See APIs, API Keys, and Third-Party Services.

90.5 What the spec is for

A spec, or PRD (product requirements document), is a short description of what the app must do, written before the code. It is one or two pages, not a novel. It matters even more with an AI:

  • Claude reads it in every session, so it builds what you decided, not what it guesses.
  • When Claude suggests a feature that isn’t in the spec, you can say no.
  • Its “how we’ll test it” list tells you when you’re done.

If you change your mind, change the spec first, then the code. An example spec is in AI-Assisted Development: From Chatbots to Coding Agents.

90.6 Milestones

The instructor will announce the due dates.

Milestone What you do What’s due
1. Proposal and spec Choose and scope your idea. Write docs/spec.md with Claude. Create the app from the starter and run it on your computer. Push it to a new GitHub repository. A one-paragraph proposal (approved by the instructor before you build), the repository link, and the spec in it
2. Database and sign-in Create a Supabase project (the same settings as Classes 10–12, step (C)). Write migrations for your 2-3 tables, with RLS policies, and push them with the Supabase CLI. Check that sign-up and login work. Migrations in supabase/migrations, and a note in the README on how you tested that one user can’t see another user’s rows
3. Core feature Build the main workflow, end to end, on your computer. Test it with made-up data and at least two test accounts. The workflow working on localhost, with a commit for each working step
4. Deploy Put the app on Vercel, add the two NEXT_PUBLIC_ variables, and update Supabase’s Site URL and redirect URLs (Classes 10–12, step (K)). Test it again online with a new account. The live Vercel URL
5. Final demo Finish the README and write your reflection. Show the app in class. Everything in the next section, and a 3-5 minute demo

Test RLS on purpose: sign up as two users (one in a private browser window), add rows as each, and check that neither sees the other’s rows. RLS is explained in Step 9: Set Up Supabase Database.

Optional extras, only after milestone 4 works: “Sign in with Google” (Classes 10–12, step (D)), an AI feature with the OpenAI API (Step E, with the same $5 limit), or payments with Stripe in test mode (Step F). Add each one to your spec first.

90.7 Deliverables

Submit these by the final deadline:

  1. The GitHub repository link. The instructor must be able to see it (make it public, or add the instructor as a collaborator).
  2. The live Vercel URL, with a test account the instructor can use (a made-up email and password, written in your submission, not in the repository).
  3. README.md, replacing the starter’s README: what the app does and for whom, the live URL, the tables, how to run it, and how you tested it.
  4. docs/spec.md, updated to match what you built.
  5. docs/reflection.md (400-600 words, in your own words): how you worked with Claude, one thing the AI got wrong and how you noticed and fixed it, and what you would do differently.

90.9 Rules

  • AI use is expected. Use Claude Code for code, commands and explanations.
  • You are responsible for the code. You approve every change, so be ready to explain any part of your app in the demo.
  • No real secrets in the repository. Keys go in .env.local and on the websites only. If a key ever reaches GitHub, tell the instructor and create a new key right away: deleting the file doesn’t remove it from Git’s history.
  • No real customer data. Use made-up names, emails and numbers, even if your idea comes from a real business.
  • Stay on free plans. The free Supabase plan allows only a few active projects, so you may have to pause your task-app project.

90.10 Key takeaways

  • Small and working beats big and broken: one workflow, 2-3 tables, one kind of user.
  • Write the spec first. It keeps you and Claude building the same thing.
  • Every table gets RLS, and you test it with two accounts.
  • Secret keys never go in the chat, in Git, or in a NEXT_PUBLIC_ variable.
  • Test on your computer first, then deploy, then test again online.

Practice Questions

Easy

Question 1 · Short answer

What is a spec (PRD), and name three things that go in this project’s spec.

Suggested answer

A spec, or product requirements document, is a short description of what the app must do, written before the code. Any three of: the problem and who has it; 3-5 user stories; the tables, their columns and who may see each row; the pages; what is out of scope for now; how you’ll test that it works.

Question 2 · Multiple choice

Which project idea is best scoped for this assignment?

  1. A marketplace where landlords list apartments and students message them
  2. A tracker where a freelancer adds clients, creates invoices and marks them paid
  3. A phone app that shows nearby food trucks on a map
  4. A store that takes real credit-card payments for three different kinds of users
Suggested answer

b. It has one kind of user, one main workflow and two tables (clients, invoices). The marketplace (a) has two kinds of users and messaging; the food-truck app (c) is a phone app with maps; the store (d) has real money and several kinds of users. All three are signs the idea is too big.

Question 3 · True or false

Because the starter template’s .gitignore excludes .env.local, it’s fine to paste your keys into Claude’s chat box so Claude can fill in the file.

Suggested answer

False. .gitignore only keeps the file out of Git. Anything you paste into the chat becomes part of the conversation, which is sent to Anthropic’s servers and saved in the session history. You paste keys into .env.local yourself; Claude only tells you where they go.

Question 5 · Short answer

What does each part of npx create-next-app@latest salon-booking -e with-supabase do?

Suggested answer

npx create-next-app@latest downloads and runs the newest version of Next.js’s app creator. salon-booking is the name of the new folder for the app’s code. -e with-supabase starts from the official example named with-supabase, which is already connected to Supabase and has sign-up and login pages. Question 6 · Scenario

Maria’s app needs an OpenAI key. Claude suggests adding NEXT_PUBLIC_OPENAI_KEY to Vercel. What should she say, and why?

Suggested answer

No. Next.js copies every NEXT_PUBLIC_ variable into the JavaScript it sends to the browser, where anyone can read it, and an OpenAI key can cost her money. A secret key belongs only on a server: in a Supabase Edge Function’s secrets (as the task app does) or in a Vercel variable without the NEXT_PUBLIC_ prefix. The prompt’s rule “never put a secret key in a NEXT_PUBLIC_ variable” covers this.

Question 7 · Scenario

Sam’s café app has a stock_counts table. How should he test that its RLS policies work?

Suggested answer

Sign up as two different test users, for example one in a normal window and one in a private window. Add rows as each user, then check that each user sees only their own rows and can’t change the other’s. A good answer also says he uses made-up data, and writes down in the README how he tested it.

Question 8 · Multiple choice

Halfway through, Sam wants to add a new column to his appointments table. What should he do?

  1. Add the column in the Supabase dashboard’s Table Editor
  2. Ask Claude to change the table directly in the database
  3. Update the spec, then have Claude write a new migration and apply it with the Supabase CLI
  4. Delete the Supabase project and start over
Suggested answer

c. The spec should match what he builds, and every database change goes through a migration file, so the change is recorded in Git and can be applied again. Changing tables in the dashboard (a) or directly (b) bypasses the migrations, so the files no longer describe the real database. Starting over (d) is unnecessary.

Hard

Question 9 · Long answer

Why does the project require you to test on your computer before deploying to Vercel, and to test again after deploying?

Suggested answer

On your computer (npm run dev), changes show up in seconds, errors appear in your terminal where Claude can read them, and nobody else sees a broken app. Fixing a problem there is faster and cheaper than on a live site. Deploying adds new things that can go wrong: Vercel’s environment variables, Supabase’s Site URL and redirect URLs, and the production build. So you test again online, with a new account, to catch problems that exist only there. A good answer separates “does my code work?” from “is the online setup right?”

Question 10 · Scenario

Maria’s spec says “users can book appointments”. In the middle of milestone 3, Claude offers to add reminder emails, a loyalty-points system and an admin dashboard “to make the app more complete”. What should she do, and how does the spec help?

Suggested answer

Say no for now, and ask Claude to finish the main workflow. The spec defines what she agreed to build, and those features aren’t in it, so they would add work, new bugs and usage before her MVP works. If she wants one later, she adds it to the spec first (perhaps under “version 2”), after milestone 4. Her prompt also tells Claude not to add anything that isn’t in the spec without asking.

Question 11 · Scenario

Sam notices that a commit he pushed to GitHub yesterday contains his .env file with a Supabase secret key. He deletes the file and pushes again. Is the problem solved? What should he do?

Suggested answer

No. Deleting the file creates a new commit, but the old commit, with the key in it, is still in the repository’s history on GitHub, where anyone who can see the repository can find it. He should create a new secret key in Supabase right away so the old one stops working, tell the instructor, and make sure .gitignore excludes the file. To prevent it, check git status before every commit, as the prompt tells Claude to do.

Question 12 · Long answer

The rules say “You are responsible for the code.” Why does that matter when an AI wrote most of it, and what habits from this page help you meet it?

Suggested answer

The AI can make mistakes: wrong commands, missing RLS policies, a key in the wrong place, features nobody asked for. You approved each change, you publish the app, and its users trust you with their data, so the mistakes are yours. Habits that help: Manual mode, reading each command before you approve it; asking Claude to explain each step; a spec that you can check the app against; migrations and RLS tests; testing locally and online; small commits that are easy to undo; and the reflection, which makes you notice what the AI got wrong.
