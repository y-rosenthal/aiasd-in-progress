Where this fits

This project is the first of three:

  1. Build the app from the video (starting today). The code is already written; your job is to set up the services it depends on, run it on your computer, and put it online.
  2. Change it. You’ll make a significant change to the app’s database and update the app to match.
  3. Build your own. You’ll build an app for your own business idea from scratch, using the same architecture (Next.js, Supabase and Vercel).

The tutorial chapters, starting with Tutorial - intro and Project Architecture, explain each piece in more depth. This page is the checklist to follow. Where it differs from those chapters, follow this page: the chapters were written for an older version of these services and are being updated.

Where to type commands: the terminal

A terminal is a window where you type commands instead of clicking. The program inside it that reads your commands is called a shell. In this course the shell is Bash: on Windows you get it with Git, as Git Bash. Macs use zsh by default, which works the same as Bash for every command on this page. (More in Getting Bash on Your Computer (Mac and Windows).)

How to read this page:

  • A gray box with a copy button in its top right corner is a command, for example:

    node --version

    Click into a terminal, type the command (or copy and paste it), and press Enter. Then wait until the prompt (the line ending in % or $) comes back before you type the next command.

  • The boxes under The prompt to start with are not commands. You paste them into Claude’s chat box.

  • Lines that start with /, such as /model sonnet, are Claude Code commands. Type them in Claude’s chat box too, not in the terminal.

  • When a step says “Claude runs” a command, Claude types it in the terminal for you after asking your permission. You don’t type it.

  • Ctrl+C in a terminal stops the command that is running (for example the app’s server). It’s Ctrl+C on every computer, including Macs.

  • If Claude is running in a terminal window, that window is busy with Claude. To type a command yourself, open a second terminal (a new window or tab), or ask Claude to run the command for you.

Reading a command

Don’t just copy commands: on this page each one is explained piece by piece, so you know what you’re asking your computer to do. Every command has the same parts. Take this one, from Step 0:

mkdir -p ~/projects/full-stack-demo-app
  • The first word is the command, the program to run. mkdir is short for “make directory” (a directory is a folder).
  • Words that start with - or -- are options: they change how the command works. -p tells mkdir to also make any missing folders on the way (here, projects), and not to complain if the folder already exists.
  • The rest are arguments: what the command works on. Here, the folder to make.
  • Spaces separate the pieces. That’s why our folder and file names have no spaces in them.
  • ~ means your home folder: /Users/maria on Maria’s Mac, /c/Users/sam in Sam’s Git Bash on Windows, and /home/ followed by your user name on Linux.
  • / separates folder names. ~/projects/full-stack-demo-app means the folder full-stack-demo-app, inside projects, inside your home folder. That is a path: directions to a folder or file.
  • Capital letters matter. task-app and Task-App are different names.

Tip: type the first few letters of a folder or file name and press Tab. The shell finishes the name for you, with no typos.

Using Claude Code without running out of usage

As of Oct 13, 2026 · Official docs: Manage costs effectively · Model configuration · Claude Fable models on your plan

The Pro plan has a usage limit that resets every five hours, plus a weekly limit. This project takes many steps, so spend your usage wisely:

  • Use Sonnet. On Pro, Claude Code’s default model is Opus 5.5, which uses up your limit faster. Type /model sonnet at the start of each session. Sonnet 5.5 handles every step of this project.
  • Switch to Opus only when you’re stuck. If Sonnet fails to fix the same error twice, try /model opus for that problem, then switch back.
  • Haiku (/model haiku) is the cheapest. It’s fine for quick questions such as “what does this error mean?”
  • Never use Fable on the Pro plan. Fable isn’t included in Pro; it is billed separately as extra usage. Don’t turn on extra usage (usage credits).
  • Keep effort at medium (the default). Check it with /effort.
  • Check your usage with /usage. It shows how much of your five-hour and weekly limits you’ve used and when they reset.
  • Start fresh between big steps. /clear empties the conversation, so Claude doesn’t re-read a long history with every message. Your progress is safe in checklist.md (see the prompt below).
  • Don’t paste huge error logs. Paste the last 20 or so lines, or tell Claude to look at the terminal output itself.
  • Put related requests in one prompt. Instead of five messages (“do A”, then “now B”, …), send one with a numbered list: “1. … 2. … 3. …”. Claude works out the order and often does several at once. It saves usage because every message makes Claude re-read the whole conversation so far, and every answer adds to it: one message with five requests means one re-read and one answer, instead of five of each. Keep the requests related, send separately anything that depends on what you decide after seeing an earlier result, and check at the end that each one was done.
  • One zoomed-out screenshot beats several. Claude reads small print well, so zoom the page out (Ctrl and -, on a Mac Cmd and -) until everything you want to show fits on the screen, and send one screenshot. To give Claude a picture, paste it into the prompt (Ctrl+V; on Windows Alt+V), drag the file in, or type its path (Work with images). If the text gets so small that Claude says it can’t read it, zoom back in on that part. Never rely on a screenshot for an exact value such as a key or an ID: one misread character (l or I, 0 or O) breaks it, so copy the text instead (and never show Claude a secret key at all).
  • Read before you approve. When Claude asks permission to run a command, read what it is about to do, and usually answer plain Yes (When Claude asks permission; Permissions, Modes, and Safety).

More details are in Context, Models, Effort, and Usage in Claude Code.

    Why? What are Supabase, an organization and a project?

    Supabase is a back end as a service: instead of renting a server and installing a database on it, you get a ready-made back end on Supabase’s computers, with a database (PostgreSQL) for the app’s data, user accounts (sign-up and login), file storage for uploaded images, and Edge Functions, small programs of your own that run on Supabase’s servers.     A project is one complete back end for one app: its own database, its own users, its own keys and its own web address. An organization holds projects, like a company holds departments: it has the billing plan and the team members who may work on its projects. The free plan allows only a few active projects, so if you used Supabase before, you may have to pause or delete an old project.

    Why? The database password and the region

    The database password is the password of the PostgreSQL database itself. The app never uses it: the app talks to Supabase with API keys (step 3). You need the password only for tools that connect to the database directly, such as the Supabase CLI when it creates your tables in Step G. Anyone who has it can read and change all of your data, so keep it only in the worksheet.

    The region is where Supabase’s data center for your project is. Data takes time to travel, so a region close to your users makes the app faster. (Companies also choose regions for legal reasons, for example to keep Europeans’ data in Europe.) “Americas” lets Supabase pick a data center in the Americas.

    Why? The three Security settings (Data API, exposed tables, RLS)
    • The Data API is a web API that Supabase creates for your database automatically. The app’s code in the browser reads and changes tables by sending web requests to your project’s address, instead of connecting to the database directly. Without it, the app couldn’t reach its data.
    • Automatically expose new tables gives the Data API permission to use each new table. The app’s database setup (its migrations, Step G) creates its tables but doesn’t grant those permissions itself; it relies on this setting. With it off, every request would fail with “permission denied”. (Supabase recommends turning it off so that you grant access to each table yourself; this older code wasn’t written that way.)
    • Row Level Security (RLS) is a set of rules, stored in the database, about which rows each user may see or change, for example “a user sees only their own tasks”. It matters because the Data API is open to anyone who has the publishable key, and that key is inside the app’s web pages, where anyone can read it. RLS is what keeps one user out of another user’s data. Enable automatic RLS turns RLS on for every new table, so a table someone forgets to protect is locked (it looks empty) instead of open to everyone. The app’s own tables have RLS rules already; see Step 9: Set Up Supabase Database.

    Why? What happens when someone signs in with Google

    Signing in with Google is a trip with several stops. Each address you enter in this form is one of them:

    1. On your app (http://localhost:3000) the user clicks Sign in with Google.
    2. The app sends the browser to Supabase, which sends it on to Google’s sign-in page. Supabase tells Google two things: your Client ID (which app is asking) and the redirect URI (where Google should send the answer).
    3. The user signs in at Google and agrees to share their name and email.
    4. Google checks that the redirect URI is on this client’s list, and only then sends the browser there, with a one-time code.
    5. The redirect URI is Supabase’s callback page. Supabase gives Google the code plus your Client secret (which proves the request really comes from your app), and gets the user’s name and email in return. Then Supabase creates or updates the user and sends the browser back to your app, to an address on the redirect-URL list you made in Step C6 (http://localhost:3000/**).

    That’s why Supabase needs the Client ID and secret (Step D7), and why the redirect URI points to Supabase, not to your app.

    Why? JavaScript origins, redirect URIs, and URI vs URL
    • URI or URL? A URL (Uniform Resource Locator) is a web address, such as https://supabase.com/docs. A URI (Uniform Resource Identifier) is the wider term: every URL is a URI, but a URI can also be just a name that isn’t an address. Every URI in this form is a web address, so here URI and URL mean the same thing.
    • Authorized JavaScript origins lists the websites that may start a Google sign-in from code running in the browser, for example Google’s own “Sign in with Google” button. An origin is just the start of an address: scheme, host and port, with no path (http://localhost:3000, not http://localhost:3000/dashboard). If these words are new, read Anatomy of a URL and Origins, and URI vs URL. In this app, sign-in goes through Supabase, so what Google checks is mainly the redirect URI. You list your app’s origin anyway, as Supabase’s setup guide says, and in Step K you add its Vercel address too.
    • Authorized redirect URIs lists where Google may send the user after they sign in. Google refuses any address that isn’t on the list, so that nobody can trick Google into sending a signed-in user’s code to their own website.
    • Google adds the domains of these addresses (for example supabase.co) to your app’s authorized domains for you; that’s what the blue box in the form says.
    Why? Where the callback URL comes from

    You don’t choose the callback URL: Supabase decides it, and builds it from your project’s ID (the project ref, Step C3):

    https:// YOUR-PROJECT-REF .supabase.co /auth/v1/callback

    • YOUR-PROJECT-REF.supabase.co is your Supabase project’s own address. Every project has a different one.
    • /auth/v1 is Supabase’s sign-in service (Auth), version 1.
    • /callback is the page in that service that receives Google’s answer.

    The worksheet builds it for you from the project ref. Supabase also shows it on its Google settings page (Step D7), as Callback URL (for OAuth), with a copy button.

    On your own computer it’s different. Supabase can also run on your computer, in Docker (see “Deeper dive: Docker, and running Supabase on your own computer” near the end of this page). That copy has the address http://127.0.0.1:54321 (127.0.0.1 means “this computer”, like localhost; see localhost and 127.0.0.1), so its callback URL is http://127.0.0.1:54321/auth/v1/callback, and its Google settings go in the file supabase/config.toml instead of the dashboard.     How to read the JSON file

    JSON (JavaScript Object Notation) is a way to write data as plain text that both people and programs can read. You met it in APIs: programs talking to programs.

    To look at the file, drag it into a browser window. Firefox shows it neatly laid out; in Chrome, tick Pretty-print at the top. Don’t open it in VS Code while Claude Code is running there: Claude Code is told which file you have open, and this one holds a secret.

    Google saves it as one long line. Laid out, it looks like this (these values are fake):

    {
  "web": {
    "client_id": "123456789012-abc123def456.apps.googleusercontent.com",
    "project_id": "task-app-2026-maria",
    "auth_uri": "https://accounts.google.com/o/oauth2/auth",
    "token_uri": "https://oauth2.googleapis.com/token",
    "auth_provider_x509_cert_url": "https://www.googleapis.com/oauth2/v1/certs",
    "client_secret": "GOCSPX-AbCdEf123...",
    "redirect_uris": ["https://abcdefghijklmnopqrst.supabase.co/auth/v1/callback"],
    "javascript_origins": ["http://localhost:3000"]
  }
}

    How to read it:

    • { } (curly braces) hold an object: a list of name: value pairs, separated by commas. The names are in double quotes.
    • A value can be text in double quotes, a list in square brackets [ ], or another object. Here the whole file is one object with one name, "web" (the application type you chose), whose value is another object with the details.
    • client_id and client_secret are the two values you copied. project_id is your Google Cloud Project ID (Step D1).
    • redirect_uris and javascript_origins are lists, because you can enter several of each. They hold exactly what you typed in the form.
    • auth_uri and token_uri are Google’s own addresses: the sign-in page users are sent to, and the address where Supabase trades the one-time code for the user’s details (stops 2 and 5 in “What happens when someone signs in with Google” above). auth_provider_x509_cert_url is where programs get Google’s certificates, to check that an answer really comes from Google. Supabase knows all three already; you don’t enter them anywhere.

    The file is a good place to check your settings: if sign-in fails, compare its redirect_uris with the callback URL in your worksheet.

Step J: Save your work to GitHub

Ask Claude to commit your changes and push them to your fork, or do it yourself: type each of these commands in VS Code’s terminal, in the task-app folder, pressing Enter after each one. First:

git status

git status lists the files you changed or added since your last commit, and changes nothing. Make sure .env.local is not in the list: it holds your keys, and the project’s .gitignore file tells Git to ignore it. Then:

git add -A
git commit -m "Set up the task app"
git push

What they do:

  • git add -A chooses which changes go into your next commit: add stages changes, and -A (all) includes every changed, new and deleted file.
  • git commit -m "Set up the task app" saves those changes as a commit, a snapshot in your project’s history. -m gives the commit its message, in quotes; write one that says what you did.
  • git push uploads your new commits to your fork on GitHub.

Where Docker fits

You don’t need Docker for this project, but you’ll hear about it.

Deeper dive: Docker, and running Supabase on your own computer

Docker packages a program together with everything it needs (the right versions of its language, libraries and settings) into a container that runs the same way on any computer. A container image is the packaged program; a container is a running copy of it (Hosting and Deployment introduces the idea).

In this project, everything that runs on a server runs on someone else’s computers: Supabase hosts the database and Edge Functions, and Vercel hosts the website. That is why you don’t need Docker.

Professional teams often also run a complete copy of Supabase on their own laptops, to experiment without touching the real project. The Supabase CLI does this with npx supabase start, which downloads Supabase’s container images and runs them in Docker: a local database, local logins, local storage, and a local dashboard at http://localhost:54323. To try it:

  • Mac
  • Windows (Git Bash)
  • Linux

Install Docker Desktop for Mac from docker.com and start it.

Install Docker Desktop for Windows from docker.com and start it. It may ask you to turn on WSL 2, a Windows feature it needs.

Install Docker Engine with your system’s package manager (see docs.docker.com), or Docker Desktop for Linux.

Then type npx supabase start in VS Code’s terminal, in the task-app folder (start starts the local copy of Supabase; npx supabase stop stops it). Docker needs a fairly recent computer and several GB of disk space, which is why it isn’t required in this course. Docker Desktop is free for personal and educational use.
