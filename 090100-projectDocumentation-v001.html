73  73. Project Documentation: Keeping Docs Next to Your Code

A project is more than its code. Your teammates, your instructor, Claude Code and you yourself, a month from now, all need to know what the app does, how it is built and how to run it. This page lists the documents a student project should keep, says what goes in each one, and shows how to keep them true while the code changes.

In this course: a documentation book in docs/

Every team project keeps all its documentation in a Quarto book in the repository’s docs/ folder. Each chapter is a plain Markdown (.md) file. The team previews the book on its own computers. The book is not published: it is support material for building and maintaining the app. This page says who reads the docs and what each chapter says. A Documentation Book for Your Project (Quarto in docs/) shows how to create the book and keep it current.

73.1 Who reads a project’s docs

Documentation (docs) is the text that explains a project: what it is for, how its parts fit together, and how to run it. Four kinds of readers need it:

  • Your teammates, who each built only some parts.
  • Claude Code. Each new session starts without memory of earlier sessions. A short, correct docs/developer-guide.md saves Claude from reading the whole project again, and from guessing.
  • Your instructor, who grades the design document (docs/prd.md), the repository and the oral exam, and who may reinstall the app from your installation guide.
  • You, later, when you no longer remember why the team chose something.

73.2 The files to keep

Keep the docs in the same Git repository as the code, in plain Markdown files. Then every change to the docs has a commit, every teammate gets them with git pull, and Claude can read them. The course uses this layout for every team project:

my-app/
├── README.md                  what the app is, the live URL, the team,
│                              how to open the docs book (not in the book)
├── CLAUDE.md                  short rules for Claude Code (or AGENTS.md)
├── .claude/skills/project-docs/SKILL.md   how Claude keeps the docs current
├── .env.example               the names of the settings, with fake values
└── docs/                      the documentation book (Quarto)
    ├── index.md               about this documentation
    ├── prd.md                 the product requirements document (PRD):
    │                          the design document you submit
    ├── user-guide.md          how to use the app
    ├── installation-guide.md  how to install the app from nothing
    │                          (key names and where each comes from, no values)
    ├── developer-guide.md     architecture, a map of the code, the database,
    │                          decisions, tests, how to make a change
    ├── specs/
    │   └── 001-short-name.md  one spec per change, written before the change
    └── releases.md            the release tags (v0.1-shortDescription)

Each fact lives in one place, and the README links to the docs book. The sections below say what goes in each file. Earlier versions of this page used separate files (design.md, architecture.md, database.md, setup-and-keys.md, decisions.md); their contents are now in prd.md, developer-guide.md and installation-guide.md.

73.2.1 README.md

GitHub shows the README.md of the top folder under the file list on the repository’s front page, so it is the first file a visitor reads. Keep it short:

  • one or two sentences on what the app does, and for whom;
  • the live URL (your Vercel address) and a screenshot;
  • the team members, and who owns which service (Supabase, Vercel, Stripe, Google Cloud, OpenAI);
  • how to open the docs book: read the .md files in docs/ on GitHub, or run quarto preview docs on your own computer;
  • a link to docs/installation-guide.md for how to run the app.

README.md is not a chapter of the docs book. The task app’s README.md is an example of this kind of file.

73.2.2 The design document: docs/prd.md

The final project asks for a Markdown design document that describes the project from a business point of view. In this course, the design document is the product requirements document (PRD), docs/prd.md. It says:

  • the problem and the users;
  • what the app does for them: the features, written as requirements;
  • what is out of scope (what the app will not do);
  • how the business makes money (or, for a non-profit, its goals and how it helps the people it serves);
  • at least two plans for future versions.

Submit docs/prd.md as the design document. The handout asks you to update it as the project changes, so that it describes the app you submit. How to write its first version with plan mode is in Plan the first version in plan mode below. More on the PRD is in The PRD.

73.2.3 The developer guide: architecture

docs/developer-guide.md is for the people (and the AI) who change the code. It has these sections: the architecture, a map of the code, the database, the decisions, the tests, and how to make a change (The developer guide).

The architecture section names the parts of the app and says what each part does and which parts talk to each other. Start with a text diagram, as in The whole app in one picture for the task app, then give one short paragraph per part: the pages (Next.js on Vercel), Supabase (database, sign-in, storage, Edge Functions), and each outside service (Google, OpenAI, Stripe). End with one or two requests traced from the click to the database, such as “what happens when a user pays”.

73.2.4 The developer guide: the database

In the database section of docs/developer-guide.md, list every table with its columns, and the Row Level Security (RLS) rules: the rules inside the database that decide which rows each signed-in user may read or change. Supabase’s documentation describes RLS as “granular authorization rules that run inside the database”. Write each rule in plain English next to its name. From the task app:

## tasks

One row per task.

| Column      | Type    | Meaning                                |
|-------------|---------|----------------------------------------|
| task_id     | uuid    | The task's ID (made by the database)   |
| user_id     | uuid    | The user who owns the task             |
| title       | text    | Required                               |
| label       | text    | Chosen by the AI when the task is made |
| completed   | boolean | false until the user ticks it          |

RLS: "Users can CRUD own tasks". A signed-in user can read, add,
change and delete only the rows whose user_id is their own ID.

The source of truth is the migration files in supabase/migrations/. The database section is the explanation that a person can read in two minutes.

73.2.5 The installation guide: keys and setup

docs/installation-guide.md says how to install the app from nothing: the accounts and services to create, the keys, the database (with the migrations), an option to load sample data from supabase/seed.sql, the Edge Functions, and the deploy. The instructor will follow it to reinstall your app, so test it (The installation guide, Sample data).

The guide names every key and setting the app needs, and says where each one comes from, where it lives and who owns it. It never holds a value. The table in The keys in the course’s task app is a good model: key name, publishable or secret, where it lives (.env.local, Vercel’s Environment Variables, a Supabase secret), and what it is for.

Names, never values

Write STRIPE_SECRET_KEY: a Supabase secret, owned by Sam. Never paste the key itself, not even a test key, into a doc, an issue, a pull request or a chat with Claude. A key that reaches GitHub must be treated as stolen: see .gitignore and Keeping Secrets Out of Git.

More details: checking that no key slipped in

Run this in your project folder. It looks for the start of real Supabase, OpenAI, Stripe and Google secrets followed by at least 16 more characters, so a doc that only says “starts with sk_test_...” does not match:

git grep -n -E '(sk-proj-|sk_test_|sk_live_|sb_secret_|whsec_|GOCSPX-)[A-Za-z0-9_-]{16,}'

No output means that it found nothing. Each line of output is a file name, a line number and the line that looks like a key. git grep searches only the files that Git tracks, so run it after git add. It doesn’t search old commits: a key that was committed and then deleted is still in the history.

73.2.6 The developer guide: decisions

The decisions section of docs/developer-guide.md is a decision log. It records each important choice: the date, what the team decided, the reason, and the options it rejected. Professional teams call one entry an architecture decision record; Michael Nygard described the idea in a 2011 blog post. Three lines per decision are enough:

## 2026-12-01: Store menu photos in Supabase Storage
- Why: the hw6 handout requires it, and RLS can limit each restaurant to its own photos.
- Rejected: putting the photos in the repository (every change would be a commit).

In the oral exam, “why did you choose this?” is a likely question. This section holds the answers.

73.2.7 The user guide, specs and releases

Three more parts of the docs book:

  • docs/user-guide.md says how to use the app, page by page, for the people who use it (The user guide).
  • docs/specs/ holds one spec per change to the app, for example docs/specs/003-menu-photos.md. You write it in plan mode before the change: what will change, why, and how you will check it (Specs).
  • docs/releases.md lists the release tags, such as v0.1-shortDescription, and what each release added (The releases page).

73.2.8 CLAUDE.md and AGENTS.md

As of Nov 24, 2026 · Official docs: How Claude remembers your project · Best practices for Claude Code

CLAUDE.md holds instructions for Claude Code, and Claude Code loads it at the start of every session. The files in docs/ hold facts for people (and for Claude when it needs them). Keep the two apart: CLAUDE.md should be short (the docs suggest under 200 lines), so don’t copy the docs into it. Point to them instead, for example “Before you change the database, read the database section of docs/developer-guide.md”. The project skill .claude/skills/project-docs/SKILL.md holds the longer steps for keeping the docs current (A skill for the docs, Rules in CLAUDE.md). If teammates use other AI tools, put the rules in AGENTS.md, which most coding agents read. Claude Code reads AGENTS.md when the project has no CLAUDE.md; a CLAUDE.md that holds only the import line @AGENTS.md also works. What belongs in these files is in CLAUDE.md and Memory.

73.3 Plain Markdown files, built into a Quarto book

Quarto is “an open-source scientific and technical publishing system” that turns Markdown files into websites, books, PDF and Word files. This book is made with Quarto. The course uses both plain Markdown and Quarto for a project’s docs:

  • The chapters are plain Markdown (.md) files in docs/. GitHub shows them formatted, with headings, tables and working links. Claude Code reads them. You need nothing extra to write them.
  • Quarto builds the chapters into one book, with a table of contents, a search box and numbered chapters. A small file, docs/_quarto.yml, lists the chapters. Each teammate who wants to read the book this way installs Quarto and runs quarto preview docs (Create the book).
  • The book is not published. It is not on the app’s website and not on GitHub Pages. It is support material for the team, the instructor and Claude. Quarto writes the built book into docs/_book/, and the .gitignore file tells Git to ignore that folder (Preview it, don’t publish it).
Read on GitHub Read with quarto preview docs
Install anything? No Yes: Quarto
What you see One .md file at a time, formatted The whole book, with a table of contents and search
Who uses it Anyone with access to the repository The team, on its own computers

Use relative links between the chapters, such as [the database](developer-guide.md#the-database); they work on GitHub and in the Quarto book. GitHub’s documentation recommends relative links for files inside the repository.

73.4 Plan the first version in plan mode

As of Nov 24, 2026 · Official docs: Choose a permission mode: plan mode

The final-project handout suggests Claude Code’s plan mode for the first version of the design document. In plan mode, Claude reads, asks and proposes, but it does not edit your files until you approve a plan (Permissions, Modes, and Safety).

  1. Start in plan mode: press Shift+Tab until the status bar shows ⏸ plan mode on, or start a message with /plan.

  2. Describe the business idea in your own words, and ask Claude to interview you before it plans:

    We are a team of 3 business students. Our final project is a web app for
[your idea]. Before you plan anything, ask us questions, a few at a time,
about the problem, the users, what the app does for them, how the business
makes money, what is out of scope, and two ideas for future versions.
Then plan a file docs/prd.md (our product requirements document) with
those sections. Don't write any code.

  3. Answer the questions yourselves, as a team. Push back when Claude assumes something that isn’t true.

  4. Read the plan. Press Ctrl+G to open it in your text editor and change it. Choose No, keep planning to ask for changes.

  5. Approve it with Yes, manually approve edits, so you see the file before Claude writes it. Then read docs/prd.md and commit it.

The same method works for the first docs/developer-guide.md and docs/installation-guide.md once the app exists: in plan mode, ask Claude to read the code and plan those files, and to write “(ask the team)” wherever the code doesn’t say why. It also works for each spec in docs/specs/, before each change.

73.5 Keep the docs in sync with the code

As of Nov 24, 2026 · Official docs: Common workflows: handle documentation

A doc that describes last week’s app is worse than no doc: people and Claude both believe it. Three habits keep the docs correct (the details are in Keep the docs current):

  • A rule in CLAUDE.md, and the project-docs skill. Add a line such as: “After every change, follow the project-docs skill: update the matching chapter in docs/ in the same commit.” The skill (.claude/skills/project-docs/SKILL.md) says which chapter to update for each kind of change.

  • Ask before you push. Before git push (or before you open a pull request), ask:

    Compare README.md and the files in docs/ with the code and with the changes
on this branch. List every statement that is no longer true, then fix them.
Don't write any key values.

  • Read the docs in the pull request. The reviewer checks the docs with the code. If a pull request adds a table and the database section of docs/developer-guide.md didn’t change, ask why.

Read what Claude writes, as you read its code. It can describe what the code does, but it can’t know why the team decided something unless the team wrote it down.

73.6 Key takeaways

  • Keep all the docs in the repository, next to the code: README.md, a short CLAUDE.md, and a Quarto documentation book in docs/ (index.md, prd.md, user-guide.md, installation-guide.md, developer-guide.md, specs/, releases.md).
  • The chapters are plain Markdown. Quarto builds them into a book that the team previews with quarto preview docs. The book is not published.
  • docs/prd.md is the design document. The developer guide holds the architecture, the database and the decisions.
  • Docs name keys and say where they come from. They never hold key values.
  • Plan the first version of the PRD in plan mode; the team answers the questions, and Claude writes the file only after you approve.
  • Update the docs in the same commit as the code they describe (the project-docs skill); ask Claude to check them before every push.

Practice Questions

Easy

Question 1 · Matching

Match each file with what it holds.

# File What it holds
1 README.md A The architecture, the tables and Row Level Security rules, the decisions
2 docs/prd.md B How to install the app from nothing: services, key names, database, deploy
3 docs/developer-guide.md C What the app is, its live URL, the team, how to open the docs book
4 docs/installation-guide.md D The plan for one change, written before the change
5 docs/specs/004-reviews.md E The problem, the users, the features, how the business makes money
Suggested answer

1 → C, 2 → E, 3 → A, 4 → B, 5 → D.

Question 2 · True or false

“docs/installation-guide.md is a safe place for test keys, because test keys can’t take real money.”

Suggested answer

False. The guide names each key and says where it comes from and where it lives, but it never holds a value. A test key still gives access to your accounts (your Stripe test data, your OpenAI usage, your Supabase project). Anything in the repository can reach GitHub, where others can copy it.

Question 3 · Short answer

Name four kinds of readers who need a project’s docs, and one thing each of them gets from the docs.

Suggested answer

Teammates (the parts of the app they didn’t build), Claude Code (the project’s structure, without reading every file or guessing; it has no memory of earlier sessions), the instructor (what the project is and why, for grading and the oral exam), and you later (why the team made each decision).

Question 4 · Multiple choice

Where does GitHub show a repository’s README.md from the top folder?

  1. Only when you click Settings.
  2. Under the file list on the repository’s front page, formatted.
  3. Nowhere; you must download it.
  4. Only to the repository’s owner.
Suggested answer

b. GitHub shows the README, formatted, to every visitor of the repository’s front page. That is why it should have the live URL and how to run the app.

Question 5 · Short answer

What is the difference between what goes in CLAUDE.md and what goes in the files in docs/?

Suggested answer

CLAUDE.md holds short instructions for Claude Code, loaded at the start of every session (commands, rules, team habits). The docs/ files hold the facts about the project for people (and for Claude when it needs them): the PRD, the user guide, the installation guide, the developer guide, the specs and the releases. CLAUDE.md should point to the docs, not copy them, so it stays short.

Medium

Question 6 · Scenario

Maria wants the team’s docs to look good. She suggests writing them in Quarto and publishing them as a website on GitHub Pages. Sam says that plain Markdown files in docs/ are enough, with no Quarto at all. What does the course do, and why?

Suggested answer

Neither is quite right. The course keeps the docs as a Quarto book in docs/ whose chapters are plain Markdown files. So Sam is right that the chapters are .md files: GitHub shows them formatted, Claude reads them, and nobody needs to install anything to read them on GitHub. Maria is right that Quarto helps: it builds the chapters into one book with a table of contents and search, which the team previews with quarto preview docs. But the book is not published, not on GitHub Pages and not on the app’s website. It is support material for the team, the instructor and Claude, and Git ignores the built book in docs/_book/.

Question 7 · Write the entry

Your app has a table bookings with columns booking_id, user_id, class_date and paid. Its RLS policy lets users read only their own bookings. Write its entry for the database section of docs/developer-guide.md.

Suggested answer 
## bookings

One row per booking of a class.

| Column     | Type    | Meaning                              |
|------------|---------|--------------------------------------|
| booking_id | uuid    | The booking's ID                     |
| user_id    | uuid    | The user who made the booking        |
| class_date | date    | The date of the class                |
| paid       | boolean | true after Stripe confirms payment   |

RLS: a signed-in user can read only the rows whose user_id is their own ID.

A good answer has every column with a short meaning, and the RLS rule in plain English. (The types are a reasonable guess; the migration file is the source of truth.)

Question 8 · Predict the output

Sam runs this in his project folder, and nothing is printed. What does that tell him, and what does it not tell him?

git grep -n -E '(sk-proj-|sk_test_|sk_live_|sb_secret_|whsec_|GOCSPX-)[A-Za-z0-9_-]{16,}'
Suggested answer

No file that Git tracks contains something that looks like a real Supabase, OpenAI, Stripe or Google secret. It does not check files that Git doesn’t track yet (new files before git add), and it does not check keys with other formats. It also says nothing about the Git history: a key that was committed and later deleted is still in old commits.

Question 9 · Ordering

Put the steps for the first version of the design document in order: approve with “Yes, manually approve edits”; answer Claude’s questions as a team; switch to plan mode; read and commit docs/prd.md; read the plan and edit it with Ctrl+G; describe the idea and ask Claude to interview you.

Suggested answer

Switch to plan mode → describe the idea and ask Claude to interview you → answer its questions as a team → read the plan and edit it with Ctrl+G → approve with “Yes, manually approve edits” → read and commit docs/prd.md.

Question 10 · Short answer

Why is plan mode a good place to start the design document, rather than just asking Claude “write our design document”?

Suggested answer

In plan mode Claude doesn’t edit files until you approve a plan. So the team first discusses the idea, answers Claude’s questions, and reads and changes the plan. The decisions come from the team, not from Claude’s guesses. “Write our design document” makes Claude invent the business details, and the team then has a document it didn’t think through and may not be able to explain.

Question 11 · Scenario

Sam’s pull request adds a reviews table and a page that shows reviews. The pull request changes no file in docs/. What should Maria, the reviewer, say?

Suggested answer

Ask Sam to update docs/developer-guide.md (the new table, its columns and its RLS rules in the database section; the new page in the architecture and the map of the code), docs/user-guide.md (how to see reviews), and probably docs/prd.md (the new feature), in the same pull request. The change should also have a spec in docs/specs/, written before the change. Docs that are updated later are often not updated at all.

Hard

Question 12 · Explain why

“A doc that describes last week’s app is worse than no doc.” Explain this claim, and give two habits that prevent it.

Suggested answer

People and Claude believe what the docs say. With no doc, they read the code. With a wrong doc, they act on false facts: Claude may change the wrong table, or a teammate may set a key in the wrong place. Habits: a CLAUDE.md rule (and the project-docs skill) to update the matching chapter in the same commit; asking Claude to compare the docs with the code before every push; reviewers checking the docs in each pull request.

Question 13 · Find the bug

What is wrong with this part of a team’s docs/installation-guide.md?

| Key               | Where it lives        | Owner |
|-------------------|-----------------------|-------|
| OPENAI_API_KEY    | .env.local            | Maria |
| STRIPE_SECRET_KEY | sk_test_51Hx...Qz (see Slack) | Sam |
Suggested answer

Two problems. The second row holds part of a real key value: the guide must name keys, never hold values, not even part of one. And on the task app’s architecture, the OpenAI key does not live in .env.local: the Edge Function that calls OpenAI runs on Supabase and reads the key from a Supabase secret (the task app’s .env.example says never to put a secret key in .env.local). Fix: write where each key really lives, for example “Supabase secret, set with npx supabase secrets set”, and no values.

Question 14 · Compare

Compare the decisions section of docs/developer-guide.md with the commit messages in git log. Both record the history of the project. Why keep both?

Suggested answer

Commit messages record what changed, one change at a time, and there are many of them. The decision log records the few important choices, with the reason and the options that the team rejected, in one short section. To answer “why did you use Supabase Storage?” you read one entry in the decision log, instead of searching hundreds of commits that may not say why.

Question 15 · Long answer

Your team starts the final project today. Write the first README.md outline and say, for each part, why it is there.

Suggested answer

A good outline: the app’s name and one or two sentences on what it does and for whom (visitors know in seconds what it is); the live Vercel URL and a screenshot (anyone can try it); the team and who owns each service (who to ask about Stripe or Supabase); how to open the docs book (the .md files in docs/ on GitHub, or quarto preview docs) and a link to docs/installation-guide.md, so a teammate or grader can install and run it (the README is the entry point to the rest). No keys.

Question 16 · Hands-on

In your task app (or your final-project repository), start Claude Code in plan mode and ask it to plan the architecture and database sections of docs/developer-guide.md from the code. Approve the plan, then check three statements in the new sections against the code yourself. What did Claude get right, and what did you have to fix?

Suggested answer

Answers differ.
