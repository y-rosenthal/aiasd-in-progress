75  75. Step 7: Set Up OpenAI API

Click here https://platform.openai.com/docs/quickstart for the OpenAI official quickstart guide.

See below for step by step instructions.

75.1 Create OpenAI Account

  1. Go to the OpenAI Platform: https://platform.openai.com/

  2. Sign up or log in to your account.

  3. Open the Dashboard (or click on the gear for settings)

75.2 Create a “project” (optional)

All OpenAI API keys are associated with a “project”. You automatically have one “Default Project”. However, it can be helpful to create a new OpenAI “project” for every website or other product you are creating.

OpenAI “projects” allow for more control as to how your API Keys are used.

When you use a “project” …

  • you can have several people in your team share the API Key

  • you can set more fine grained permissions as to how the project can use the key

See here for more info about Open AI projects: https://help.openai.com/en/articles/9186755-managing-projects-in-the-api-platform

To create a project, do the following:

75.2.1 Click settings (gear) button

75.2.2 Select “projects”

75.2.3 Click “create”

75.2.4 Give your project a name

75.3 Create API keys

75.3.1 Click API Keys

75.3.2 Click Create new secret key.

75.3.3 Key Owner - “YOU” or a “SERVICE ACCOUNT”

When creating the key you need to specify whether the key is owned by “you” or by a “service account”. See more explanation below.

API Keys that are owned directly by “you” are useful when you are performing experiments with AI or just getting to understand how things work. In addition some 3rd part websites ask you to upload an OpenAI API key so that the work that they do for you is billed to YOUR OpenAI API key - i.e. the service doesn’t pay for the AI processing it does on your behalf, you do. It makes sense for these types of keys to be owned by “You”.

However, when creating software products that use API Keys it’s recommended to create a “Service Account” for that product and have the key be owned by that service account. The use of the key can then be tracked to your product’s “service account”.

Setting permissions for keys owned by “You”

If you create a key that is owned by “You” (see above) then you are given the opportunity to set permissions that govern what is and what isn’t allowed to be done with the key. This is especially important if you are going to be using your API Key to access 3rd party services. You can restrict the API Key to only allow some features to ensure that the 3rd party service doesn’t abuse the use of the key (as use of the API key would be charged to you).

If you create a key that is owned by a “Service Account” (as recommended for this project) then you can set permissions

Setting permissions for keys owned by a “Service Account”

By contrast, the permissions for a key that is owned by a “Service Account” are governed by the service account’s “role”. To change what the key can do, you must change the service account’s roles/permissions, not the key. We’ll see below (after saving the key) how to modify the permissions for such a key.

75.3.4 Copy the key immediately — you won’t be able to see it again.

When you click “create secret key” (see above) you will be shown the actual key. Copy the key immediately and save it — you won’t be able to see it again.

The key should be treated in the same way as a password. (In the following screenshot the API Key is purposely obscured). It is secret information which should never be divulged to anyone outside of your organization. Even within your organization, only people who have a “need to know” should be given access to the actual key value. Therefore do NOT commit this to git because git repos are often shared with people who should not have access to this type of info.

In the next section we will explain how to store this API Key in the supabase/.env file. This is because the communication with OpenAI will be done via a Supabase Edge Function. Much of the other “secret” information that we will be using in this tutorial will also be stored in .env files (see the section above that describes more about .env files).

For now, I recommend that for the purposes of this tutorial, you also store all of the secret info in a Word document (or similar). This is NOT the recommended approach for actual software development projects. However, as you are learning it can be helpful to have one file that stores all of the “secret information” in one place. You can store notes and screenshots in this file that help you remember where you got the information (e.g. OpenAI) and what it will be used for.

75.4 Setting permissions for keys owned by a “Service Account”

How to adjust permissions:

Go to Organization → Admin keys / Service accounts.

Select the service account.

Modify its assigned roles/permissions.

All keys for that service account will now reflect those updated permissions.

If you’d like, I can outline how to set up a more restrictive service account.

75.4.1 Store as Supabase Secret

You’ll configure your Edge Functions to read OPENAI_API_KEY from the Supabase environment.

  1. Install Supabase CLI (if you haven’t already)

    (see the chapter above about the Supabase CLI)

  2. Link your local project to your Supabase project (if you haven’t already)

    (see the chapter above about the Supabase CLI)

  3. Run the following command to set the secret in Supabase, where “your-openai-key” is the tet of the key that you just got from openai

    supabase secrets set OPENAI_API_KEY=your-openai-key

  4. Confirm that the key was set:

    You can run the following command to confirm that there is an OPENAI_API_KEY set to some value. However, the “DIGEST” that is shown here is NOT the actual key. This is done for security reasons. You can delete the key and reset it but you cannot see the actual value for the key.

    npx supabase secrets list
    NAME           | DIGEST                                                           
----------------|------------------------------------------------------------------
 OPENAI_API_KEY | 661627b246146bfd00805f19997db43c066fba3002fabe2ed6a9922c8db29f87

    You can also use the supabase website dashboard (Project Settings → API → Secrets) to see the same info.

Practice Questions

Easy

Question 1 · True or false

Every OpenAI API key belongs to a project, and every account automatically has a “Default Project”.

Suggested answer

True. You can use the Default Project, or create more projects, for example one for each website or product you build.

Question 2 · Multiple choice

When can you see the full value of a new OpenAI API key?

  1. Any time, on the API keys page
  2. Only once, right after you create it
  3. Whenever you run npx supabase secrets list
  4. After you ask OpenAI’s support team
Suggested answer

b. OpenAI shows the key only once, when you create it, so copy it immediately. Later, the API keys page (a) only shows a shortened version, secrets list (c) only shows a digest, and there is no way to get the key back (d): if you lose it, you create a new key.

Question 3 · Short answer

Why should an API key be treated like a password? Give two reasons.

Suggested answer
  1. Anyone who has the key can use OpenAI through your account, and that usage is charged to you.
  2. It is secret information that only people who need it should see. That is why it must never be committed to Git: repositories are often shared with people who shouldn’t have it.

Question 4 · True or false

Keeping all of your project’s secret keys in a Word document is the recommended approach for real software projects.

Suggested answer

False. The page suggests a private notes document only while you are learning, to keep track of where each value came from and what it is for. In real projects, secrets are kept in places designed for them, such as .env files that are never committed and secret storage like Supabase secrets.

Medium

Question 5 · Multiple choice

You are creating the key that task-app itself will use. According to the page, who should own this key?

  1. You, because you are the developer
  2. A service account created for the product
  3. The first user who signs up for task-app
  4. It doesn’t matter; all keys behave the same
Suggested answer

b. For software products, the page recommends a key owned by a service account, so that the key’s use can be tracked to that product (and the key isn’t tied to one person’s own account). Keys owned by “You” (a) suit your own experiments. Option c makes no sense, and d is wrong: the owner affects how use is tracked and how permissions are managed.

Question 6 · Short answer

Why might you create a separate OpenAI project for each website or product you build?

Suggested answer

Projects give you more control over how your keys are used. With one project per product, each product gets its own keys, you can set permissions for that project, you can give the right teammates access, and the use of each product’s keys stays separate.

Question 7 · Scenario

A third-party website asks you to paste in your OpenAI API key so it can do AI work for you. What should you keep in mind, and how can you limit the risk?

Suggested answer

The AI work the site does will be billed to your OpenAI account. Create a separate key just for that site (owned by “You”) and use its permissions to allow only the features the site needs, so the key can’t be used for anything else. If you stop using the site, delete that key.

Question 8 · Write the command

Your new key is sk-abc123. Write the command that stores it as a Supabase secret named OPENAI_API_KEY.

Suggested answer 
npx supabase secrets set OPENAI_API_KEY=sk-abc123

In this tutorial the Supabase CLI runs through npx, so the command starts with npx supabase.

Question 9 · Predict the output

You run npx supabase secrets list and see a row with the name OPENAI_API_KEY and the digest 661627b246146bfd.... Is the digest your OpenAI key? What does this output tell you?

Suggested answer

No. The digest is a scrambled “fingerprint” of the value, not the key itself: for security reasons, Supabase never shows the actual value. The output only confirms that a secret named OPENAI_API_KEY is set on your project. If you need a different value, you can delete the secret and set it again, but you can never read it back.

Question 10 · Short answer

Why is the OpenAI key stored as a Supabase secret rather than in .env.local?

Suggested answer

The code that talks to OpenAI runs in a Supabase Edge Function, on Supabase’s servers, so the key must be available there. secrets set stores the key in your Supabase project, where the function can read it. As a bonus, the key stays on a server and never reaches the users’ browsers.

Question 11 · Ordering

Put these steps in the right order.

  1. Run npx supabase secrets list to confirm that the secret is set
  2. Click Create new secret key and choose the key’s owner
  3. Run npx supabase secrets set OPENAI_API_KEY=...
  4. Open the API keys page on the OpenAI platform
  5. Copy the key immediately and save it in a safe place
Suggested answer

d → b → e → c → a.

Hard

Question 12 · Scenario

You accidentally pushed a file containing your OpenAI key to a public GitHub repository. What should you do, and why isn’t deleting the file from the repository enough?

Suggested answer
  1. Delete the leaked key on the OpenAI API keys page right away, so it stops working.
  2. Create a new key.
  3. Store the new key in Supabase with npx supabase secrets set OPENAI_API_KEY=<new key> (setting a secret again replaces its old value).

Deleting the file isn’t enough: the key is still in the Git history, someone may already have copied it, and anyone who uses it runs up charges on your account.

Question 13 · Scenario

You run npx supabase secrets set OPENAI_API_KEY=... and get the message Cannot find project ref. Have you run supabase link? What went wrong, and how do you fix it?

Suggested answer

Your project folder isn’t linked to your Supabase project yet (or you ran the command from a different folder), so the CLI doesn’t know which project should get the secret. Go to your project’s top-level folder, run npx supabase link --project-ref <your-project-ref>, and then run the secrets set command again.

Question 14 · Find the bug

To save time, a classmate skips the Edge Function and calls OpenAI directly from the app’s browser code, with this line in .env.local:

NEXT_PUBLIC_OPENAI_API_KEY="sk-..."

Explain the problem.

Suggested answer

In Next.js, variables whose names start with NEXT_PUBLIC_ are built into the JavaScript that is sent to every visitor’s browser. Anyone could find the key there (for example, with the browser’s developer tools) and use OpenAI at your expense. Secret keys must stay on a server; that is why this project calls OpenAI from a Supabase Edge Function and stores the key as a Supabase secret.
