83  83. Step 15: Automated Testing and Troubleshooting

Automated tests help ensure everything works after changes.

83.0.1 Integration Tests

The project includes integration tests in tests/integration/. They talk to your real Supabase project and your Stripe sandbox: they create test users, tasks and payments there. Use a test project, not one with real users.

The test files end in .test.ts (for example 2_auth.test.ts). The test runner, Jest, runs only files whose names end that way.

83.0.2 Set Up Test Environment

  1. In the project root, copy the example environment file to a new file named .env.test.local:

    cp .env.example .env.test.local

    cp copies the first file to the second. The tests read their settings from .env.test.local in the project root. Like .env.local, it is ignored by Git, so your keys stay off GitHub.

  2. Fill in all six variables:

    Variable Value
    NEXT_PUBLIC_SUPABASE_URL Your Supabase project URL
    NEXT_PUBLIC_SUPABASE_ANON_KEY Your Supabase publishable key (sb_publishable_...; older projects: the anon key)
    SUPABASE_SERVICE_KEY Your Supabase secret key (sb_secret_...; older projects: the service_role key)
    STRIPE_SECRET_KEY Your Stripe sandbox secret key (sk_test_...)
    STRIPE_PRICE_ID Your price’s ID (price_...)
    STRIPE_WEBHOOK_SECRET Your webhook’s signing secret (whsec_...)

    The Supabase secret key can read and change everything in your project, so it goes only in this file, never in .env.local or in a NEXT_PUBLIC_ variable of the app.

  3. Keep the test settings separate from production credentials.

83.0.3 Run Tests

Run all tests:

npm test

npm test runs the project’s test script, which starts Jest.

Run one test file:

npm test tests/integration/2_auth.test.ts

If you see failures due to cold starts or timeouts:

  • Run the tests again.
  • Check that your Edge Functions are deployed and reachable.

83.1 Troubleshooting

A few quick checks for common problems.

83.1.1 Environment Variables Not Loading

  • Verify the filenames:
    • Local Next.js: .env.local
    • Supabase: supabase/.env (if applicable) and Supabase secrets.
  • Restart the dev server after any env changes.
  • Confirm the variables are defined in:
    • The Next.js runtime (console.log(process.env.NEXT_PUBLIC_... )).
    • Supabase dashboard (for secrets).

83.1.2 Authentication Errors

  • Ensure your OAuth redirect URIs match exactly in:
    • Google Cloud Console (OAuth credentials).
    • Supabase Auth settings.
  • Make sure the Supabase Site URL matches your local and production URLs.
  • Inspect the browser network tab for auth-related errors.

83.1.3 Edge Functions Failing

  • Check that all required secrets are set (OPENAI_API_KEY, STRIPE_SECRET_KEY, STRIPE_PRICE_ID, STRIPE_WEBHOOK_SECRET). npx supabase secrets list shows their names.
  • In Supabase:
    • Open Edge Functions → Logs to see runtime errors.
  • Make sure code imports are correct and dependencies are installed.

83.1.4 Stripe Webhook Not Working

  • Confirm JWT verification is disabled for stripe-webhook.
  • Double-check the webhook URL in Stripe:
    • It must match the function URL exactly (including https).
  • Ensure the Signing secret in Supabase matches the current secret shown in Stripe.
  • Buy a subscription with a test card, then read the stripe-webhook logs in Supabase (see Step 11).

83.1.5 Database Errors

  • Ensure npx supabase db push ran successfully without errors.
  • Check that RLS policies allow the operation you’re trying.
  • Confirm that the user is authenticated when performing actions that require auth.
  • Inspect Supabase logs or use the SQL editor to run queries manually.

Practice Questions

Easy

Question 1 · Short answer

What is an integration test, and what is its advantage over clicking through the app yourself after every change?

Suggested answer

An integration test is a small program that checks that several parts work together - here, the app’s code with your real Supabase project (database, storage, edge functions). Because the tests are automated, one command re-runs all of them after every change, the same way every time. Clicking through by hand is slow, and it’s easy to forget a step.

Question 2 · Write the command

Write the command that runs all of the project’s automated tests.

Suggested answer 
npm test

Run it from the project root.

Question 3 · Multiple choice

Which file holds the environment variables for the Next.js app when you run it on your own computer?

  1. .env.local
  2. package.json
  3. .gitignore
  4. README.md
Suggested answer

a. The troubleshooting checklist names .env.local for local Next.js. package.json (b) lists the project’s packages and scripts, .gitignore (c) lists the files Git should ignore (including .env.local itself), and README.md (d) is documentation.

Question 4 · True or false

It’s fine to point the integration tests at your production Supabase project, the one that holds real users’ data.

Suggested answer

False. The tests create, change and delete real records (users, tasks, payments) in whatever project they are pointed at. That is why the page says to use a test project, not one with real users, and to keep the test settings separate from production credentials.

Medium

Question 5 · Write the command

The project contains the test file tests/integration/3_storage.test.ts. Following the pattern on this page, write the command that runs only this file.

Suggested answer 
npm test tests/integration/3_storage.test.ts

npm passes the file name on to the test tool, Jest, which then runs only that file. (npm test -- tests/integration/3_storage.test.ts works too: the -- tells npm that everything after it is for the test tool, not for npm.)

Question 6 · Short answer

A test fails with a timeout the first time you run the tests, then passes when you run them again right away. What is a likely cause, and what does the page suggest?

Suggested answer

A cold start: an edge function that hasn’t been used for a while needs a moment to start up, so the first request can be slow enough to hit the test’s time limit. On the second run the function is already “warm” and answers quickly. The page suggests running the tests again, and checking that your edge functions are deployed and reachable.

Question 7 · Multiple choice

Your deployed edge functions need keys such as OPENAI_API_KEY. Where do they read these values from?

  1. The supabase/.env file on your laptop
  2. The secrets stored in your Supabase project (set with npx supabase secrets set ...)
  3. The environment variables of your Vercel project
  4. The .env.local file
Suggested answer

b. Deployed functions run on Supabase’s servers, which can’t read files on your laptop - not even supabase/.env (a). The values must be stored in the Supabase project as secrets. Vercel’s variables (c) and .env.local (d) are for the Next.js app, not for edge functions. To see which secrets are set, run npx supabase secrets list (it shows their names, not their values).

Question 8 · Matching

Match each symptom with the section of the troubleshooting checklist you would turn to first.

Symptom Checklist section
1. On the live site, after signing in with Google you land on localhost A. Database Errors
2. Saving data fails with an error that mentions a “row-level security policy” B. Edge Functions Failing
3. Stripe test payments succeed, but nothing changes in your database C. Environment Variables Not Loading
4. AI labels stopped appearing, and the function’s logs show errors D. Authentication Errors
5. You added a new key to .env.local, but the app still behaves as if it isn’t there E. Stripe Webhook Not Working
Suggested answer

1 → D, 2 → A, 3 → E, 4 → B, 5 → C.

Hard

Question 9 · Scenario

You deleted your old Stripe webhook endpoint and created a new one with the correct URL. Stripe now delivers events to your stripe-webhook function, but the database is never updated, and the function’s logs show a signature-verification error. What’s wrong, and how do you fix it?

Suggested answer

Every Stripe webhook endpoint has its own signing secret (whsec_...). Your new endpoint got a new secret, but Supabase still holds the old one in STRIPE_WEBHOOK_SECRET, so the function can’t verify the signatures and rejects every event. Fix: copy the new endpoint’s signing secret from the Stripe Dashboard and store it in Supabase:

npx supabase secrets set STRIPE_WEBHOOK_SECRET=whsec_...

This is the checklist item “Ensure the Signing secret in Supabase matches the current secret shown in Stripe”.

Question 10 · Scenario

Clicking “Sign in with Google” takes you to a Google error page that says Error 400: redirect_uri_mismatch. What is the most likely cause, and what exactly would you compare?

Suggested answer

The Authorized redirect URI saved in Google Cloud Console doesn’t exactly match the callback address that Supabase uses. Compare the URI in your OAuth credentials in Google Cloud Console with Supabase’s callback URL, which has the form https://[your-project-ref].supabase.co/auth/v1/callback. They must match character for character: look for a wrong project ref, http instead of https, a typo in /auth/v1/callback or an extra / at the end.

Question 11 · Scenario

Maria signs in and opens the dashboard, but her task list is empty. In the Supabase Table Editor you can see rows in the tasks table that belong to her. Using the “Database Errors” checklist, what two things would you check, and why might there be no error message at all?

Suggested answer

Check that (1) the app’s request really is made as the signed-in user - a request without Maria’s sign-in information counts as anonymous - and (2) the RLS policies on tasks allow users to read their own rows. With row level security, rows you aren’t allowed to see are simply left out of the results, so the app gets an empty list instead of an error. The Table Editor shows the rows because the Supabase dashboard looks at the data with full admin rights, which RLS does not limit.
