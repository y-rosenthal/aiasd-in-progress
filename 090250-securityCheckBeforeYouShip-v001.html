77  77. A Security Check Before You Ship

Your app is online, and your repository may be public. Anyone can read everything the browser receives and send any request to your back end. This page lists the main risks of an app like yours, the checks you can run, how to use Claude Code to find and fix problems, what an AI review can miss, and when a professional must look at the app. Background: secret keys (Publishable and Secret Keys), .env files (.gitignore and Keeping Secrets Out of Git), and prompt injection (Limits, Risks, and Responsible Use).

77.1 The main risks for an app like yours

Risk What can happen How to check
A secret key in the repository Anyone copies it and spends your money or reads all your data Check 1
A secret key in the browser The same: every visitor can read it Check 2
A table without Row Level Security (RLS) Any visitor reads, changes or deletes every user’s rows Check 3
Trusting the browser A user changes the price, their plan, or the user ID in a request Ask Claude (below)
Server code that doesn’t check who calls it Anyone calls your Edge Function or API route, for example to run your AI feature for free Ask Claude (below)
A webhook that doesn’t check Stripe’s signature A fake “payment succeeded” message makes a user Premium Ask Claude (below)
An AI feature without limits Someone runs thousands of requests on your OpenAI credit, or tricks the AI with instructions hidden in their input Limits (below)
File uploads without limits Huge files, harmful file types, or a bucket whose file list anyone can read Check 3 and the bucket settings
Packages with known vulnerabilities An attacker uses a published weakness in a library your app uses Check 4

Three rules explain most of this table:

  • The browser is not trusted. Every decision that matters (the price, who may see a row, how many AI requests a user gets) is made on a server or in the database. In the task app, the price comes from a setting of the create-stripe-session Edge Function, and a database trigger enforces each user’s monthly task limit; the page can’t change either.
  • Least privilege. Each part gets only the access it needs. The browser gets the publishable key; only server code gets secret keys.
  • Limit the cost of abuse. Keep a small prepaid OpenAI balance, turn off auto recharge (OpenAI turns it on by default during setup), and limit the number of AI requests per user. (OpenAI says that access may not stop the moment the credit runs out, so a small overrun is possible.) As of Nov 24, 2026 · Official docs: OpenAI: What is prepaid billing?

77.2 Check 1: no secret keys in the repository

In your project folder, list the tracked files whose names contain “env”:

git ls-files | grep -i env

Output in the task app (only the templates with fake values are tracked):

.env.example
.env.test.example

Then check that Git ignores your real settings file, and which .gitignore line does it:

git check-ignore -v .env.local

Output:

.gitignore:67:.env*.local   .env.local

No output means that Git does not ignore the file: fix .gitignore first. (git log --all --oneline -- .env.local .env with no output means the files were never committed.) Last, search the tracked files for the beginnings of secret keys, followed by at least 20 more characters (a real key is long; a placeholder such as sk_test_XXXX is short):

git grep -nE "(sk_live_|sk_test_|sb_secret_|whsec_)[A-Za-z0-9]{20,}|sk-proj-[A-Za-z0-9_-]{20,}"

No output is the result you want; the task app gives none. If a line appears, treat that key as leaked: replace it at the service that issued it, and then clean up (If you leak a secret).

77.3 Check 2: no secret keys in the browser

As of Nov 24, 2026 · Official docs: Next.js: Bundling environment variables for the browser · Supabase: API keys

When Next.js builds the app, it copies the value of every NEXT_PUBLIC_ variable that the browser code uses into the JavaScript files that every visitor downloads. So a secret key must never have a name that starts with NEXT_PUBLIC_. The build puts those files in the folder .next/static. After npm run build, search them:

grep -rlE "sk_live_|sk_test_|sk-proj-|sb_secret_|whsec_" .next/static

No output is the result you want. When we tested this with a fake OpenAI key in a NEXT_PUBLIC_ variable that a page used, the command listed two files:

.next/static/chunks/app/dashboard/page-c68bc559c9484696.js
.next/static/chunks/app/task/page-d440192bf7af7c01.js

Your publishable keys (sb_publishable_...) are in these files, and that is expected. Supabase refuses its secret keys when they come from a browser, but a leaked secret key still works from any other program, so replace it.

77.4 Check 3: Row Level Security on every table

As of Nov 24, 2026 · Official docs: Supabase: Advisors · Supabase: Row Level Security

Your project’s URL and publishable key are in the browser. So the database’s RLS policies are the only thing that stops a visitor from reading every user’s data (how the task app’s policies work: Enable Row Level Security).

  1. Run the Security Advisor. In the Supabase dashboard, open the Security Advisor (under Advisors). It checks your project for known problems. Fix every finding, or ask Claude to explain why it doesn’t apply. Findings to look for include:
    • Table publicly accessible (level ERROR): RLS is off, so “anyone with your project URL can read, edit, and delete all data in this table”.
    • Security policy allows unrestricted access: a policy such as USING (true) lets every user see every row.
    • No access rules defined: RLS is on, but no policy exists, so the app can’t read the table.
    • A public storage bucket whose files anyone can list.
  2. Test as a different user. Sign in as user A (one Google account) and create some data. Sign in as user B (a second account, in a private window). User B must not see A’s data, and must not open it by pasting the address of A’s page. Ask Claude to write this as an automated test.

77.5 Check 4: packages with known vulnerabilities

As of Nov 24, 2026 · Official docs: npm audit · GitHub: Configuring Dependabot alerts

npm audit asks npm’s registry for known vulnerabilities in the packages your project uses. --omit=dev leaves out the development tools, which never reach your users:

npm audit --omit=dev

Reports are common, even for the course’s task app. Don’t run npm audit fix --force on your own: it can install versions your code doesn’t work with. Ask Claude: “Explain which of these vulnerabilities affect my app, update what is safe, then run npm run build and the tests.” On GitHub, the owner can turn on Dependabot alerts (Settings, Advanced Security, Dependabot alerts, Enable) to get warnings about vulnerable packages.

Also check two settings: your Stripe keys start with sk_test_ and pk_test_ (test mode only; never sk_live_), and your storage bucket has a file size limit and a list of allowed file types, as the task app’s bucket does (1 MB, images only).

77.6 Ask Claude to review the whole app

As of Nov 24, 2026 · Official docs: Commands: /security-review · Catch security issues as Claude writes code

/security-review in Claude Code looks for security problems such as injection, authentication mistakes and data exposure. It reviews only the changes on your current branch compared with the default branch on GitHub, so run it on a branch before you open a pull request (AI in the Pull Request Workflow). To review the whole app, ask in plain words:

Do a security review of this whole project before we submit it. Check:
1. Secret keys: in any tracked file, or in a NEXT_PUBLIC_ variable.
2. Row Level Security: on every table, and what each policy allows.
3. Every Edge Function and API route: does it check who is calling?
4. Anything the app trusts from the browser: prices, user IDs, plans, limits.
5. The Stripe webhook: does it check Stripe's signature?
6. The AI feature: limits per user, and what happens with harmful input.
7. File uploads: size limits, allowed types, who can read and list files.
List each problem with the file, the risk in plain English, and how bad it
is. Don't change any files yet.

Then fix the problems one at a time: ask Claude to explain the fix, make it, run npm run build and the tests, and repeat the check that found the problem. When all are fixed, ask for a new review.

More details: two Claude Code plugins for security
  • The security-guidance plugin makes Claude check its own changes for common vulnerabilities while it works.
  • The Claude Security plugin (/claude-security) runs a deeper scan of a whole repository with several agents, and suggests patches that you review. It needs a paid plan (on Pro, turn on dynamic workflows in /config), and each scan uses your plan’s usage.

Install them as described in Plugins. As of Nov 24, 2026 · Official docs: Scan your codebase for vulnerabilities

77.6.1 What an AI review does well, and what it can miss

An AI review reads every file quickly, knows the common mistakes, and explains them plainly. Use it every time. But:

  • It can be wrong or incomplete. Anthropic’s documentation for its security-guidance plugin says that the review “can miss issues”, and calls the plugin “not a complete security solution”.
  • It sees only what you show it. Anthropic’s documentation says that a review in Claude Code reads the source code in your folder, “not a running site or deployed service”. Settings that you changed in the Supabase, Vercel or Stripe dashboards aren’t in the code.
  • It doesn’t know your business rules, for example that a coach may see their own clients’ records but not other coaches’ clients.
  • “No problems found” is not proof that there are none.

You are responsible for what you ship, and you must be able to explain each check in the oral exam.

77.7 A professional security review

Before your app has real users, real payments or real personal data (names, addresses, health or financial data), a qualified security professional must review it. Such a review can include a penetration test, in which testers “mimic real-world attacks” to find ways past the app’s security (NIST). The checks on this page, and AI reviews, do not replace it. For this course, you use Stripe’s test mode only, so a class project doesn’t reach this point. If you continue your app as a business, it does.

77.8 The prototype option

The professional review may find deep problems: for example, every page talks to the database with no clear rules, or secret keys are spread over many places. Then treat your app as a working prototype. It has done its job: it proves the idea, the features, the screens and the business rules. Build the product again from the ground up, with AI’s help, and with a professional security approach from the start:

  1. Write down the security requirements first: who may see and change what, which data is sensitive, which laws apply.
  2. Design a secure architecture: what runs on the server, what the browser may do, where each key lives.
  3. Give each part the least privilege it needs.
  4. Review at each step, with tests and AI checks after every change.
  5. Involve security professionals in the design and before launch.

Why can rebuilding be cheaper and safer than patching? The OWASP Top 10, a standard list of web-application risks, says that “an insecure design cannot be fixed by a perfect implementation” (OWASP: Insecure Design). Patches on a weak design leave gaps, and each new patch can open another. With AI, writing code again is fast. The expensive part is the decisions, and the prototype has already made most of them.

77.9 Key takeaways

  • The browser is not trusted: secret keys, prices, limits and access rules live on the server or in the database.
  • Check that no secret key is in the repository (git ls-files, git check-ignore, git grep) or in the browser bundle (grep in .next/static).
  • Every table needs Row Level Security: run the Security Advisor and test as a second user.
  • /security-review checks only your branch’s changes; ask Claude for a whole-app review, fix one problem at a time, and check again.
  • AI reviews can miss problems and don’t see dashboard settings. Before real users, payments or personal data, a professional must review the app; if the design is weak, rebuild it from the prototype with security designed in.

Practice Questions

Easy

Question 1 · Multiple choice

Which environment variable name puts its value into the JavaScript that every visitor’s browser downloads, if the browser code uses it?

  1. STRIPE_SECRET_KEY
  2. NEXT_PUBLIC_SUPABASE_URL
  3. SUPABASE_SECRET_KEY
  4. OPENAI_API_KEY
Suggested answer

b. Next.js copies the values of NEXT_PUBLIC_ variables into the browser code when it builds the app. The other three names have no NEXT_PUBLIC_ prefix, so the browser code doesn’t get them; that is where secret keys belong (and in the task-app architecture, they live in Supabase, not in Next.js at all).

Question 2 · True or false

“If Claude Code’s security review finds no problems, the app is secure.”

Suggested answer

False. An AI review can be wrong or incomplete, it reads only the code in your folder (not the settings in the Supabase, Vercel or Stripe dashboards), and it doesn’t know your business rules. “No problems found” is not proof.

Question 3 · Short answer

What does the Supabase Security Advisor finding “Table publicly accessible” mean, and why is it serious?

Suggested answer

Row Level Security is off for that table. Anyone with the project’s URL (which is in the browser) can read, change and delete every row in it, including other users’ data.

Question 4 · Fill in the blank

In test mode, Stripe secret keys start with ______. A key that starts with ______ is a live key, which your class project must never use.

Suggested answer

sk_test_; sk_live_.

Question 5 · Short answer

What is a penetration test?

Suggested answer

A test in which security professionals imitate real attacks on the app to find ways past its security. It is part of a professional security review, which an app needs before it has real users, real payments or real personal data.

Medium

Question 6 · Write the command

Write the command that shows whether Git ignores .env.local, and which line of which file makes it ignored. What does no output mean?

Suggested answer 
git check-ignore -v .env.local

It prints the file, the line number and the pattern (for example .gitignore:67:.env*.local). No output means Git does not ignore the file, so the next git add . could commit your keys.

Question 7 · Predict the output

Sam built his app with npm run build and ran grep -rlE "sk_live_|sk_test_|sk-proj-|sb_secret_|whsec_" .next/static. It printed one file name. What does this mean, and what must he do?

Suggested answer

A secret key is in the JavaScript that every visitor downloads, most likely because a NEXT_PUBLIC_ variable holds a secret key and the browser code uses it. He must move that work to server code (for example an Edge Function) with a variable that has no NEXT_PUBLIC_ prefix. If that version was ever deployed, he must also replace the key at the service that issued it, because anyone may have copied it.

Question 8 · Scenario

Maria’s app has worked on a branch for two days. She runs /security-review on main right after a teammate merged everything and pushed. Why might the review find nothing, and what should she do?

Suggested answer

/security-review reviews only the changes on the current branch compared with the default branch on GitHub. On an up-to-date main, there are no such changes. She should run it on each feature branch before its pull request, and ask Claude in plain words for a review of the whole project.

Question 9 · Scenario

Your app stores customers’ orders. Describe how to test that one customer can’t see another customer’s orders.

Suggested answer

Sign in as user A (one Google account) and create an order. In a private window, sign in as user B (a second account). Check that B doesn’t see A’s order in any list, and that pasting the address of A’s order page shows nothing. Then ask Claude to turn this into an automated test, so it is checked after every change.

Question 10 · Short answer

npm audit reports 20 vulnerabilities, and suggests npm audit fix --force. What do you do instead, and why?

Suggested answer

Run npm audit --omit=dev to see only the packages that reach users, and ask Claude to explain which vulnerabilities affect the app and to update what is safe, then run npm run build and the tests. --force can upgrade packages to versions that the code doesn’t work with, and break the app.

Question 11 · Matching

Match each risk with the protection.

Risk Protection
1. A fake “payment succeeded” message A. A limit on AI requests per user, and a small prepaid balance
2. A user changes the price in the request B. The webhook checks Stripe’s signature
3. Someone runs your AI feature thousands of times C. Row Level Security policies
4. A visitor reads other users’ rows D. The server takes the price from its own settings
Suggested answer

1 → B, 2 → D, 3 → A, 4 → C.

Hard

Question 12 · Long answer

Explain why “the browser is not trusted” with an example from your own app idea. What must run on the server instead?

Suggested answer

Everything the browser receives can be read, and everything it sends can be changed, with the developer tools or a small script. Example: a tutoring app whose page sends “price: 40” with the booking. A user changes it to 1. So the server (an Edge Function) must look up the price itself, check who the user is from their login, and decide what they may book. Access rules belong in Row Level Security, and limits (such as AI requests per month) in the database or the server.

Question 13 · Scenario

Claude’s whole-app review says “No security problems found.” But the Security Advisor shows “Security policy allows unrestricted access” on the orders table. How can both be true, and what do you do?

Suggested answer

Claude reads the code in your folder. If the policy was created or changed in the Supabase dashboard and not in a migration file, Claude doesn’t see it; it may also simply have missed it. Trust the finding: show Claude the advisor’s message and the policy, ask it to explain the risk and write a policy that lets each user see only their own orders (in a migration file), then run the Security Advisor again and test as a second user.

Question 14 · Long answer

A professional review of your team’s app finds that each page talks to the database in its own way, with no clear access rules, and that keys are in several places. Explain the prototype option, and why it can be cheaper and safer than patching.

Suggested answer

Treat the app as a working prototype: it proved the idea, the features, the screens and the business rules. Build the product again from the ground up, with AI’s help: write down the security requirements first (who may see and change what, which data is sensitive), design a secure architecture (what runs on the server, where each key lives), give each part the least privilege it needs, review at each step, and involve security professionals. It can be cheaper and safer because patches can’t fix an insecure design (OWASP: “an insecure design cannot be fixed by a perfect implementation”), each patch can open new gaps, and with AI the code itself is fast to write again; the decisions, which are the expensive part, are already made.

Question 15 · Scenario

After the course, your team wants to switch the app to Stripe’s live mode and sign up real customers next month. List what you would do first.

Suggested answer

Run all the checks on this page (secrets in the repository and the browser, RLS with the Security Advisor and a second user, dependencies, the webhook signature, limits on the AI feature and uploads) and a whole-app AI review, and fix what they find. Then have a qualified security professional review the app, including a penetration test, before real users, real payments or real personal data. If the review finds deep design problems, rebuild the app from the prototype with security designed in.

Question 16 · Compare

Compare /security-review, a plain-words whole-app review by Claude, and a professional penetration test. What does each look at?

Suggested answer
  • /security-review: the code changes on your current branch, compared with the default branch on GitHub. Quick; use it before each pull request.
  • A whole-app review by Claude: all the code in your folder, guided by the list of risks you give it. It doesn’t see dashboard settings or the running site, and it can miss problems.
  • A penetration test: professionals attack the running app the way real attackers would, including its settings and services, and find ways past its security. It is needed before real users, payments or personal data.
