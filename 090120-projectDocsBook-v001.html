74  74. A Documentation Book for Your Project (Quarto in docs/)

Every project in this course keeps all of its documentation in one place: a small documentation book in the repository’s docs/ folder. This page shows what goes in the book, how to set it up with Quarto, and how to make Claude Code keep it up to date after every change. What each document should say is in Project Documentation.

74.1 Why a documentation book?

The documentation book is support material for building and maintaining your app. It is not part of the app, and you don’t publish it: it is not on your app’s website and not on GitHub Pages. Its readers are:

  • your teammates, who need to know how the app works and how to run it;
  • Claude Code, which reads the docs at the start of a task;
  • your instructor, who will reinstall your app from scratch by following your installation guide;
  • you, a month from now, when you have forgotten why you made a choice.

The chapters are ordinary Markdown files (.md). GitHub shows them formatted, Claude reads them like any other file, and Quarto (the tool that builds this course book) turns them into a book with a table of contents, search and working links, which you look at on your own computer.

74.2 What’s in the book

my-app/
├── README.md                  what the app is, the live URL, the team
├── CLAUDE.md                  rules for Claude Code (see below)
├── .claude/skills/project-docs/SKILL.md   how to keep the docs current
├── supabase/seed.sql          sample data (optional, see the installation guide)
└── docs/                      the documentation book
    ├── _quarto.yml            the book's settings and its list of chapters
    ├── index.md               about this documentation
    ├── prd.md                 product requirements document
    ├── user-guide.md          how to use the app
    ├── installation-guide.md  how to install the app from scratch
    ├── developer-guide.md     how the app is built, and how to change it
    ├── specs/
    │   └── 001-sign-in-and-orders.md   one spec for each change
    └── releases.md            the list of releases (tags)
Chapter Who it is for What it answers
Product requirements Everyone What problem does the app solve, for whom, and what must it do?
User guide The app’s users How do I use the app?
Installation guide Your instructor, a new teammate How do I install this app from nothing?
Developer guide Teammates, Claude Code How is the app built, and how do I change it safely?
Specs Teammates, Claude Code What exactly will the next change do?
Releases Everyone Which versions exist, and what changed in each?

74.3 Create the book

As of Nov 24, 2026 · Official docs: Quarto: Get started · Quarto: Books

  1. Install Quarto from quarto.org/docs/get-started.

    • Mac

    Download the macOS installer (.pkg) and open it. ## Windows (Git Bash) Download the Windows installer (.msi) and run it. Then close Git Bash and open it again, so that it finds the new quarto command. ## Linux Download the .deb file (Ubuntu, Debian) and install it, for example with sudo apt install ./quarto-*.deb in the folder where you saved it.

    Check that it works:

    quarto --version

  2. Make the folder and the files. In your project’s folder, create docs/ with the files in the tree above. The quickest way is to ask Claude Code:

    Create a Quarto documentation book in docs/ with these chapters as Markdown (.md) files: index.md, prd.md, user-guide.md, installation-guide.md, developer-guide.md, a part "Specs for changes" with specs/001-<first change>.md, and releases.md. Fill each chapter from what you can learn from the code, and mark every place where you need information from us. Add docs/.gitignore with /.quarto/ and /_book/. Don't publish it anywhere.

    Then read every file: Claude’s first version always has gaps and guesses.

  3. Check docs/_quarto.yml. It lists the chapters in order. A tested example:

    project:
  type: book
  output-dir: _book

book:
  title: "Mugs by Sam: Project Documentation"
  author: "Maria Lopez and Sam Lee"
  chapters:
    - index.md
    - prd.md
    - user-guide.md
    - installation-guide.md
    - developer-guide.md
    - part: "Specs for changes"
      chapters:
        - specs/001-sign-in-and-orders.md
    - releases.md

format:
  html:
    theme: cosmo
    toc: true

  4. Keep the built book out of Git. docs/.gitignore has two lines:

    /.quarto/
/_book/

    Only the .md files and _quarto.yml are committed. Each person builds the book on their own computer.

74.4 Preview it, don’t publish it

To read the book, in your project’s folder (type cd to it first) run:

quarto preview docs

Quarto builds the book into docs/_book/ and opens it in your browser, at a localhost address. It rebuilds the page each time you save a file. Press Ctrl+C in the terminal to stop it. quarto render docs builds the book once and lists problems such as broken links, which is a quick check after a change.

Never publish the documentation book
  • Don’t turn on GitHub Pages for the repository (GitHub can publish a docs/ folder as a website).
  • Don’t copy docs/_book/ into your app’s public/ folder. A Next.js app serves only public/ and its own pages, so docs/ never reaches your app’s website by itself.
  • If the repository is public, anyone can still read the .md files on GitHub. So never write a key, password or token in the docs.

74.5 Product requirements document (PRD)

docs/prd.md describes the app from a business point of view. It is the final project’s design document:

  • the problem, and who the customers or users are;
  • what the app does for them: the features, as numbered requirements (“R3: A signed-in user can upload a photo of a mug, up to 5 MB”);
  • what is out of scope (what the app deliberately does not do);
  • how the business makes money, or, for a non-profit, its goals;
  • at least two plans for future versions.

Plan the first version in plan mode (Plan the first version in plan mode). Keep it true: when a feature changes, the PRD changes.

74.6 Specs for changes

Before each change to the app, write a short spec in docs/specs/, one file per change, numbered in order (002-stripe-payments.md, 003-photo-upload.md):

# Spec 003: Photo upload

**Status:** planned          (later: done, in release v0.3-photoUpload)

## Goal
Sellers can add a photo to each mug.

## What the user sees
An "Add photo" button on the mug's page; the photo appears in the list.

## Changes
- Database: column `photo_path` in `mugs`; a storage bucket `mug-photos`, private.
- Code: the mug page and the upload form.
- Services and keys: none new.

## How to check it
- Upload a 2 MB JPEG: it appears. Upload a 20 MB file: an error message.
- Another user can't see a private photo.

Ask Claude Code to draft the spec in plan mode, read it, change it, and only then let Claude change the code. Add each new spec to docs/_quarto.yml.

74.7 The installation guide

docs/installation-guide.md must let someone who has none of your accounts install the app from scratch: your instructor will follow it, step by step, to reinstall your app. Write it in this order:

  1. What you need: the tools (Git, Node.js, the Supabase CLI) and the accounts (Supabase, Vercel, Stripe in test mode, Google Cloud for sign-in, OpenAI).
  2. Get the code: git clone ..., npm install.
  3. Each service, one step at a time: create the Supabase project; set up Google sign-in; create the Stripe test products and the webhook; create the OpenAI key. Say exactly what to click and what to copy.
  4. The keys: a table with each environment variable’s name, where its value comes from, and where it goes (.env.local, Vercel, Supabase secrets). Never the values.
  5. The database: link the project and apply your migrations (supabase link, then supabase db push). Create the storage buckets if your migrations don’t. Deploy the Edge Functions and set their secrets.
  6. Sample data (optional): see the next section.
  7. Run it, then deploy it: npm run dev, then the Vercel steps.
  8. Check it: a short list of things to try (sign in, create an item, pay with a test card, upload a file).

Test the guide: a teammate who didn’t write it follows it on a new Supabase project. Every place where they get stuck is a fix to the guide.

74.7.1 An option to load sample data

As of Nov 24, 2026 · Official docs: Supabase: Seeding your database · Supabase CLI: db push

Keep sample data (a few products, categories, example records) in supabase/seed.sql: INSERT statements only, no table definitions. The migrations create the tables; the seed file fills them. Then the installation guide offers a choice:

  • Without sample data: supabase db push (the tables are empty).
  • With sample data: supabase db push --include-seed (applies the migrations, then runs the seed file).

Rows that belong to a user (for example, a user’s orders) need that user to exist first. Explain in the guide how to create a test account and then add its sample rows, for example with a SQL snippet in the Supabase SQL Editor that uses the test account’s email. Never put real people’s data in the seed file.

74.8 The developer guide

docs/developer-guide.md explains how the app is built, so a teammate (or Claude) can change it safely:

  • Architecture: each part (browser, Next.js on Vercel, Supabase, Stripe, OpenAI, Google), where it runs, and how they talk to each other.
  • Code map: which folder holds what.
  • Database: each table and column in plain English, and its Row Level Security rules (“a user sees only their own orders”).
  • Decisions: dated, short entries (“2026-12-01: photos go in Supabase Storage, not in the database, because …”).
  • How to make a change: a branch, a spec, a pull request, the docs, a tag.
  • How to test: npm run build, npm test, what to check by hand.

74.9 The user guide

docs/user-guide.md is for the people who use the app: how to sign up, each main task in a few steps, with screenshots, and the Stripe test card to use for payments. Your demo video can follow it.

74.10 The releases page

Each time you release a version, tag it in Git (Tags and Releases) and add it to docs/releases.md, newest first:

## v0.2-stripePayments (2026-12-03)
- Users can buy a mug with Stripe (test mode). Spec 002.
- Fixed: the order list showed other users' orders.

74.11 Keep the docs current

Docs that are out of date mislead your teammates and Claude. Make updating them part of every change, and let Claude Code do the work:

  1. Write a spec before the change.
  2. After the change, and before every push, Claude updates every doc the change touches and runs quarto render docs.
  3. A teammate who reviews the pull request also checks the docs.

Two files make this automatic: a project skill and a few rules in CLAUDE.md. (This course book is maintained the same way.)

74.11.1 The skill: .claude/skills/project-docs/SKILL.md

As of Nov 24, 2026 · Official docs: Extend Claude with skills · How Claude remembers your project

A skill is a folder with a SKILL.md file: a name and a description (which tell Claude when to use it), then instructions (Skills). Commit it, so every teammate’s Claude uses it. A starting version to copy and adapt:

---
name: project-docs
description: Keep this project's documentation book (docs/, a Quarto book) up to date. Use after any change to the app's features, code, database, services, keys, setup or deployment; before every push; when writing a spec for a change; when making a release; and when the user asks about the docs.
---

# The documentation book (docs/)

All of this project's documentation is a Quarto book in `docs/`. Its chapters
are Markdown files listed in `docs/_quarto.yml`. The book is NOT published:
never turn on GitHub Pages for it, never copy `docs/_book/` into `public/`,
never deploy it.

## Which file holds what
| File | Holds |
|---|---|
| docs/prd.md | The product requirements: problem, users, numbered requirements, out of scope, business model, future versions |
| docs/user-guide.md | How to use the app, for its users |
| docs/installation-guide.md | How to install the app from scratch, with and without sample data (supabase/seed.sql); key NAMES and where each comes from, never values |
| docs/developer-guide.md | Architecture, code map, database (tables, columns, RLS), decisions, how to test and change the app |
| docs/specs/NNN-name.md | One spec per change: goal, what the user sees, changes, how to check it, status |
| docs/releases.md | Every release tag, newest first, with what changed |

## Before a change
1. Write a spec in docs/specs/ (the next number) and add it to docs/_quarto.yml.
2. Show it to the user. Change code only after the user approves it.

## After a change, and before every push
1. See what changed: `git status` and `git diff --stat main...HEAD`.
2. Update every doc the change touches:
   - a feature: the user guide, the PRD, and the spec's status;
   - a table, column or RLS rule: the developer guide (and a migration);
   - a new service, key or setup step: the installation guide (and supabase/seed.sql if sample data changes);
   - a design choice: a dated entry in the developer guide's decisions.
3. Run `quarto render docs` and fix every warning.
4. Tell the user in a few lines what you updated.

## A release
When the user asks for a release: list the changes since the last tag
(`git log --oneline LAST_TAG..HEAD`), propose a name `vX.Y-shortDescription`,
add an entry to docs/releases.md, commit, create an annotated tag with the
list as its message, and push the commit and the tag.

## Rules
- Never write a key, password or token in any doc.
- Write the installation guide for a reader who has none of our accounts:
  our instructor must be able to reinstall the app from it alone.

74.11.2 Rules in CLAUDE.md

Add a short section to the project’s CLAUDE.md (CLAUDE.md and Memory):

## Documentation
- All documentation is a Quarto book in docs/ (not published; preview with
  `quarto preview docs`). Follow the project-docs skill.
- Before you change the app, write a spec in docs/specs/ and wait for approval.
- After every change, and before every push, update the docs that the change
  touches and run `quarto render docs`.
- Never put keys, passwords or tokens in the docs or in any committed file.

Then test it: make a small change, ask Claude to push, and check that it updates the docs first.

74.12 Key takeaways

  • All of a project’s documentation lives in a Quarto book in docs/: the PRD, the user guide, the installation guide, the developer guide, specs for changes, and the releases page.
  • The chapters are Markdown files. You preview the book with quarto preview docs; you never publish it, and the built docs/_book/ is not committed.
  • The installation guide lets someone install the app from scratch, with or without sample data (supabase db push --include-seed).
  • A spec comes before each change; the docs are updated after each change and before each push.
  • A project-docs skill and a few CLAUDE.md rules make Claude Code do this every time. Never write a key in the docs.

Practice Questions

Easy

Question 1 · Multiple choice

Where does a project’s documentation book live, and who reads it?

  1. On the app’s website, for its customers.
  2. In the repository’s docs/ folder, for the team, Claude Code and the instructor.
  3. In a Google Doc that the team shares.
  4. On GitHub Pages, for anyone on the internet.
Suggested answer

b. The book is support material for building and maintaining the app. It is not published, so a and d are wrong. A Google Doc (c) isn’t in the repository, so Claude can’t read it next to the code and it doesn’t change with the code.

Question 2 · Matching

Match each question to the chapter that answers it.

Question Chapter
1. How do I install this app from nothing? A. prd.md
2. What must the app do, and for whom? B. developer-guide.md
3. Which table stores the orders, and who may read them? C. installation-guide.md
4. What will the next change do, and how do we check it? D. specs/004-....md
Suggested answer

1 → C, 2 → A, 3 → B, 4 → D.

Question 3 · Write the command

You are in your project’s folder. What command shows the documentation book in your browser, and rebuilds a page when you save it?

Suggested answer

quarto preview docs. Press Ctrl+C to stop it.

Question 4 · True or false

“The documentation book’s chapters must be written in a special Quarto format, so GitHub can’t show them.”

Suggested answer

False. The chapters are ordinary Markdown (.md) files. GitHub shows them formatted, Claude reads them, and Quarto builds them into a book.

Medium

Question 5 · Short answer

Why does docs/.gitignore list /_book/?

Suggested answer

docs/_book/ is the built book (HTML files) that Quarto makes from the .md files. It can be rebuilt at any time, so only the sources are committed. Each person builds the book on their own computer with quarto preview docs or quarto render docs.

Question 6 · Write the command

Your installation guide offers two ways to set up the database. What command applies the migrations and loads the sample data from supabase/seed.sql? What command applies only the migrations?

Suggested answer

With sample data: supabase db push --include-seed. Without: supabase db push. (Both run after supabase link has connected the CLI to the Supabase project.)

Question 7 · Find the bug

Sam’s installation guide has this table row:

Name Value Where
STRIPE_SECRET_KEY sk_test_51Pq... Supabase secrets

What is wrong, and how should the row look?

Suggested answer

It contains a key’s value. Docs never hold keys, even test keys: the repository may be public, and Git keeps old versions forever. The row should give the name, where the value comes from (for example “Stripe dashboard, test mode → Developers → API keys → Secret key”) and where it goes. Sam should also replace the key in Stripe, because it was exposed.

Question 8 · Short answer

What goes in a spec, and when do you write it?

Suggested answer

Before the change. It has the goal, what the user will see, the changes (database, code, services, keys), how to check that it works, and a status (planned, then done with the release tag). You ask Claude to draft it in plan mode, then read and correct it before any code changes.

Question 9 · Scenario

Maria added a reviews table with a migration, and a “Write a review” button. Which docs must change?

Suggested answer

The developer guide (the new table, its columns and its RLS rules), the user guide (how to write a review), the PRD (the new requirement), the spec for this change (status done), and, if sample reviews help a tester, supabase/seed.sql and the installation guide’s sample-data step. When it is released, the releases page too.

Hard

Question 10 · Long answer

Your instructor will reinstall your app from scratch by following your installation guide. List what the guide must cover, in order, and explain how your team can test it before you submit.

Suggested answer

In order: the tools and accounts needed; getting the code (git clone, npm install); setting up each service step by step (Supabase, Google sign-in, Stripe test products and webhook, OpenAI); a table of environment variable names, where each value comes from and where it goes (no values); the database (supabase link, supabase db push, buckets, Edge Functions and their secrets); the sample-data option (--include-seed, and how to add rows for a test user); running and deploying; a checklist of things to try.

To test it, a teammate who didn’t write it follows it exactly on a new Supabase project (and a new Vercel project). Each place where they get stuck or have to guess becomes a fix to the guide.

Question 11 · Compare

What does the project-docs skill do that a rule in CLAUDE.md alone does not, and why have both?

Suggested answer

CLAUDE.md is loaded in every session, so it should stay short: a few rules (“update the docs before every push; follow the project-docs skill”). The skill holds the detailed steps (which file holds what, the steps before and after a change, how to make a release), and Claude loads it only when it is needed, so it doesn’t use context all the time. The rule makes sure Claude remembers to do it; the skill says exactly how.

Question 12 · Scenario

A teammate turns on GitHub Pages for the repository “so the docs look nice online”. The repository is public. What are the problems, and what should the team do instead?

Suggested answer

The documentation book is support material, not part of the product, and the course says not to publish it. Published docs can describe internal details (the database’s security rules, admin steps) to anyone. GitHub Pages also adds a second website that the team must maintain. Turn GitHub Pages off; each person reads the book locally with quarto preview docs. In any case, the docs must never contain keys, because the .md files in a public repository can be read on GitHub.
