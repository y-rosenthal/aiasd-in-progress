Classes 10–12: The Task App, Start Here

Classes 10–12, starting Tuesday, October 13, 2026

About the “Class Meetings” section

This section has one page for each meeting of our class this semester. Each page lists the date, the topic, and what we did, with links to the chapters that explain the material. Use it to review, or to catch up on a class you missed.

Topic: We start building the full-stack “task app” from the tutorial video. I demonstrate each step at the front of the room while you do the same steps on your own laptop. You type every command and do every step on the websites yourself, following these pages, as developers did before AI tools: that’s how you learn what each piece does. When you get stuck, ask Claude for help (When you’re stuck: ask Claude). You won’t finish today. Pick up where you left off at home or in our next class, as I’ll announce.

Where this fits

This project is the first of three:

  1. Build the app from the video (starting today). The code is already written; your job is to set up the services it depends on, run it on your computer, and put it online.
  2. Change it. You’ll make a significant change to the app’s database and update the app to match.
  3. Build your own. You’ll build an app for your own business idea from scratch, using the same architecture (Next.js, Supabase and Vercel).

The tutorial chapters, starting with Tutorial - intro and Project Architecture, explain each piece in more depth. This page and the step pages it links to are the checklist to follow. Where they differ from those chapters, follow these pages: the chapters were written for an older version of these services and are being updated.

We’ll use VS Code, a free code editor. One window shows:

  • a terminal at the bottom (Terminal > New Terminal), where you type every command, such as npm install (see the next section);

Where to type commands: the terminal

A terminal is a window where you type commands instead of clicking. The program inside it that reads your commands is called a shell. In this course the shell is Bash: on Windows you get it with Git, as Git Bash. Macs use zsh by default, which works the same as Bash for every command on this page. (More in Getting Bash on Your Computer (Mac and Windows).)

How to read this page:

  • A gray box with a copy button in its top right corner is a command, for example:

    node --version

    Click into a terminal, type the command (or copy and paste it), and press Enter. Then wait until the prompt (the line ending in % or $) comes back before you type the next command.

  • The boxes under When you’re stuck: ask Claude are not commands. You paste them into Claude’s chat box.

  • Lines that start with /, such as /model sonnet, are Claude Code commands. Type them in Claude’s chat box too, not in the terminal.

  • Ctrl+C in a terminal stops the command that is running (for example the app’s server). It’s Ctrl+C on every computer, including Macs.

  • A terminal where Claude is running is busy with Claude. Type your commands in a different terminal (a new window or tab).

  • Commands for the app itself (from Step B5 on) must run in the app’s folder, task-app. Before you type one, go into that folder:

    cd ~/projects/full-stack-demo-app/task-app

    cd means “change directory”: go into a folder. After cd, the following commands run in that folder. It’s harmless if you’re already there, so when in doubt, type it again. To check where you are, type pwd (“print working directory”): it prints the folder’s full path, which should end in /task-app. Don’t go by the prompt: it looks different on every computer (The prompt explains why, and how to make yours the same as everyone’s).

You can use two kinds of terminal: your computer’s terminal app, and the terminal built into VS Code (described after these tabs). Until VS Code is installed (Step A5), use the terminal app.

  • Mac
  • Windows (Git Bash)
  • Linux

  • VS Code’s terminal: Terminal > New Terminal. It also runs zsh.
  • Paste into either one with Cmd+V.
  • The Git Bash app: open the Start menu, type Git Bash, and press Enter. The prompt ends in $.
  • VS Code’s terminal: Terminal > New Terminal, after Step A5 makes Git Bash its default. The label at the right side of the terminal panel should say bash. If it says powershell, redo the last part of Step A5.
  • Paste: in VS Code’s terminal, Ctrl+V. In the Git Bash app, Ctrl+V does not paste: use Shift+Insert, or right-click and choose Paste.
  • Don’t use PowerShell or Command Prompt for this page. Their prompts look like PS C:\Users\sam> or C:\Users\sam>, and the commands here are written for Bash. (The one exception is installing Claude Code, in Step A3.)
  • The Terminal app: press Ctrl+Alt+T (on Ubuntu and many other versions of Linux), or search your apps for Terminal. It runs Bash.
  • VS Code’s terminal: Terminal > New Terminal. It also runs Bash.
  • Paste into either one with Ctrl+Shift+V. (Plain Ctrl+V doesn’t paste in a Linux terminal.)

Reading a command

Don’t just copy commands: on this page each one is explained piece by piece, so you know what you’re asking your computer to do. Every command has the same parts. Take this one, from Step 0:

mkdir -p ~/projects/full-stack-demo-app
  • The first word is the command, the program to run. mkdir is short for “make directory” (a directory is a folder).
  • Words that start with - or -- are options: they change how the command works. -p tells mkdir to also make any missing folders on the way (here, projects), and not to complain if the folder already exists.
  • The rest are arguments: what the command works on. Here, the folder to make.
  • Spaces separate the pieces. That’s why our folder and file names have no spaces in them.
  • ~ means your home folder: /Users/maria on Maria’s Mac, /c/Users/sam in Sam’s Git Bash on Windows, and /home/ followed by your user name on Linux.
  • / separates folder names. ~/projects/full-stack-demo-app means the folder full-stack-demo-app, inside projects, inside your home folder. That is a path: directions to a folder or file.
  • Capital letters matter. task-app and Task-App are different names.

Tip: type the first few letters of a folder or file name and press Tab. The shell finishes the name for you, with no typos.

Using Claude Code without running out of usage

As of Oct 13, 2026 · Official docs: Manage costs effectively · Model configuration · Claude Fable models on your plan

The Pro plan has a usage limit that resets every five hours, plus a weekly limit. This project takes many steps, so spend your usage wisely:

  • Use Sonnet. On Pro, Claude Code’s default model is Opus 5.5, which uses up your limit faster. Type /model sonnet at the start of each session. Sonnet 5.5 handles every step of this project.
  • Switch to Opus only when you’re stuck. If Sonnet fails to fix the same error twice, try /model opus for that problem, then switch back.
  • Haiku (/model haiku) is the cheapest. It’s fine for quick questions such as “what does this error mean?”
  • Never use Fable on the Pro plan. Fable isn’t included in Pro; it is billed separately as extra usage. Don’t turn on extra usage (usage credits).
  • Keep effort at medium (the default). Check it with /effort.
  • Check your usage with /usage. It shows how much of your five-hour and weekly limits you’ve used and when they reset.
  • Start fresh for a new problem. /clear empties the conversation, so Claude doesn’t re-read a long history with every message. Then paste the help prompt again (When you’re stuck).
  • Don’t paste huge error logs. Paste the command you typed and the last 20 or so lines of what it printed.
  • Put related requests in one prompt. Instead of five messages (“do A”, then “now B”, …), send one with a numbered list: “1. … 2. … 3. …”. Claude works out the order and often does several at once. It saves usage because every message makes Claude re-read the whole conversation so far, and every answer adds to it: one message with five requests means one re-read and one answer, instead of five of each. Keep the requests related, send separately anything that depends on what you decide after seeing an earlier result, and check at the end that each one was done.
  • One zoomed-out screenshot beats several. Claude reads small print well, so zoom the page out (Ctrl and -, on a Mac Cmd and -) until everything you want to show fits on the screen, and send one screenshot. To give Claude a picture, paste it into the prompt (Ctrl+V; on Windows Alt+V), drag the file in, or type its path (Work with images). If the text gets so small that Claude says it can’t read it, zoom back in on that part. Never rely on a screenshot for an exact value such as a key or an ID: one misread character (l or I, 0 or O) breaks it, so copy the text instead (and never show Claude a secret key at all).
  • You run the commands, not Claude. If Claude asks permission to run a command or change a file, answer No and ask it to tell you what to type (If Claude asks permission).

More details are in Context, Models, Effort, and Usage in Claude Code.

Before the steps: make the project folder

Everything for this project goes in one folder, full-stack-demo-app, inside the projects folder in your home folder. Make it now:

Ask your question. Each time, give Claude what it needs to see what you see:

  • Which step you’re on, for example “I’m on step G”.
  • For a terminal command: the command you typed and everything it printed, as text. Select it in the terminal with the mouse, copy it, and paste it into Claude’s chat box. Text is better than a screenshot: Claude reads every character exactly. (In VS Code’s Claude panel, you can instead type @terminal: and choose the terminal, and Claude reads its output.)
  • For a website: a screenshot. Paste it into Claude’s chat box with Ctrl+V (on Windows Alt+V), or drag the image file in.
  • What you expected and what happened instead.

Claude can also look at your worksheet and your screenshot log, to see which steps you’ve done and what you entered. Say, for example, “Look at my screenshot log for step D.”

Tell Claude how much to explain. If an answer goes too fast, say “explain more” or “one step at a time, please”. If it explains something you already know, say “I already know how to do that”. Claude adjusts for the rest of the conversation.

Keys in Claude’s chat

In this course it’s fine for Claude to see your keys, in your worksheet or in what you paste: they belong to a practice app, with test-mode payments and a $5 limit on OpenAI. In a real project, keep secret keys out of AI chats and anything else you share (Publishable and Secret Keys).

If Claude asks permission

In Manual mode, Claude stops and asks “Do you want to proceed?” before it runs a command or changes a file. Read what Claude says the command is for, then choose with the arrow keys and press Enter:

  • Yes, if the command only looks at something: for example, it reads your worksheet or screenshot log, or lists the files in a folder.
  • No, if it would do one of your steps for you or change anything (install something, change a file, or run a command from a step). Then type: “Please tell me what to type instead.”

If you’re not sure which it is, choose No and ask Claude what the command does. Claude reads the app’s code and your course notes without asking.

  • Don’t press Shift+Tab in Claude’s chat box. It switches to the next mode (Manual, then accept edits, then plan, then auto). If the line under the chat box no longer says manual mode on, press Shift+Tab until it does.
  • More about permissions and the modes: Permissions, Modes, and Safety.

The steps

Work through these steps in order, after making the project folder. Type every command yourself (or copy it from the page or the worksheet), and read what it means before you press Enter. The notes also tell you where the older tutorial chapters are wrong.

  • (A) Install the tools (10–20 min)
  • (B) Get the code onto your computer (5–10 min)
  • (C) Supabase project and the front end (15–25 min)
  • (D) Sign in with Google (15–25 min)
  • (E) OpenAI API key, with a $5 limit (10–15 min)
  • (F) Stripe, in test mode (10–20 min)
  • (G) Create the database (5 min)
  • (H) Deploy the Edge Functions and the Stripe webhook (10–15 min)
  • (I) Try the app (10–15 min)
  • (J) Save your work to GitHub (5 min)
  • (K) Put the app online with Vercel (10–20 min)
  • (L) Optional: automated tests, and Docker (tests 5–10 min, Docker 20–40 min)

All together, steps A to K take about 2 to 3 hours, spread over Classes 10–12. The times include taking the screenshots for your log, but not reading the optional “Why?” boxes or fixing problems.
