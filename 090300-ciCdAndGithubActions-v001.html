78  78. CI/CD and GitHub Actions

Every time you push, a computer can build and test your app and show the result on the pull request. This page explains CI/CD, shows a small GitHub Actions workflow for a Next.js app, and explains why AI coding agents make CI both more important and more expensive.

78.1 CI and CD in plain English

Continuous integration (CI) means that every push and every pull request starts an automatic check: a clean computer downloads the code, installs the packages, builds the app and runs the tests. If a step fails, the team knows within minutes. CI catches “it works on my machine” problems, such as a file you forgot to commit or a type error in a file you didn’t open.

CD has two meanings (Atlassian explains both):

Term What happens after the checks pass
Continuous delivery The change is ready to release, but a person decides when to release it (for example, by clicking a button).
Continuous deployment The change goes live automatically. No person approves each release.

You already have continuous deployment. Your final project is connected to Vercel (Hosting and Deployment). Vercel builds every push. A push to main (the production branch) becomes the live site if the build succeeds; a failed build doesn’t replace the live site. A push to any other branch, or a pull request, gets a preview deployment with its own address. Vercel also reports each deployment on GitHub as a commit status, so a pull request already shows whether Vercel could build it.

As of Nov 24, 2026 · Official docs: Vercel: Environments · Vercel for GitHub: Commit status

Vercel doesn’t run your tests, and it doesn’t stop a pull request from being merged. That is the job of CI.

78.2 GitHub Actions: the parts

GitHub Actions is GitHub’s built-in automation service. You describe what to do in a YAML file (a plain-text settings format that uses indentation to show structure) in the folder .github/workflows/ of your repository.

  • A workflow is one such file, for example .github/workflows/ci.yml.
  • A trigger (the on: key) says which event starts it: push, pull_request, a schedule, a button, and others.
  • A workflow has one or more jobs. Each job runs on a fresh runner: a virtual machine that GitHub starts for the job and deletes afterwards.
  • A job is a list of steps. A step either runs a command (run:) or uses a ready-made action (uses:), such as actions/checkout, which downloads your code onto the runner.
 git push / open a PR
        |
        v
 GitHub reads .github/workflows/ci.yml   ("on: pull_request" matches)
        |
        v
 runner (fresh Ubuntu VM):  checkout -> setup Node -> npm ci -> npm run build -> npm test
        |
        v
 result shown as a check on the commit and the pull request:  green check / red X

78.3 A first workflow for a Next.js app

As of Nov 24, 2026 · Official docs: Quickstart for GitHub Actions · actions/checkout · actions/setup-node

Save this as .github/workflows/ci.yml in your project, commit it, and push:

name: CI

on:
  push:
    branches: [main]
  pull_request:

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
      - uses: actions/setup-node@v7
        with:
          node-version: 24
          cache: npm
      - run: npm ci
      - run: npm run build
      - run: npm test --if-present
Line What it does
on: push: branches: [main] Run after every push to main
pull_request: Run for every pull request, and again for each new push to it
build: The job’s name; it is also the name of the check on the pull request
runs-on: ubuntu-latest Use a GitHub-hosted Linux runner
actions/checkout@v7 Download the repository onto the runner
actions/setup-node@v7 Install Node.js 24; cache: npm saves the downloaded packages between runs
npm ci Install exactly the versions in package-lock.json (a clean install)
npm run build Build the app, as Vercel does; type errors fail here
npm test --if-present Run the test script if package.json has one; otherwise do nothing

@v7 is the action’s major version (the newest for both actions as of Nov 24, 2026). Use the same major Node.js version as your Vercel project (the project’s Settings → Build and Deployment → Node.js Version). Without --if-present, npm test fails with Missing script: "test" when there is no test script. The file passes actionlint, a checker for workflow files.

Why? The build needs some environment variables

Your .env.local file is not in Git, so the runner doesn’t have it. Some apps can’t even build without certain variables. For example, the course’s task app reads NEXT_PUBLIC_SUPABASE_URL in next.config.mjs. Without it, npm run build stops with TypeError: Invalid URL. With NEXT_PUBLIC_SUPABASE_URL and NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY set, the build succeeds. The fix is to store them as repository secrets (next section) and pass them to the job:

jobs:
  build:
    runs-on: ubuntu-latest
    env:
      NEXT_PUBLIC_SUPABASE_URL: ${{ secrets.NEXT_PUBLIC_SUPABASE_URL }}
      NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY: ${{ secrets.NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY }}

Tests that sign up users or charge test cards (the task app’s integration tests) need a real database and test keys, so they fail on a runner without them. In CI, run only the tests that need no keys.

78.4 Watching it run, and requiring it to pass

As of Nov 24, 2026 · Official docs: Status checks · Available rules for rulesets

  • The Actions tab lists every workflow run. Click a run, then the job (build), to see each step’s log. When a step fails, read its first error, or paste it into Claude Code.
  • On a pull request, each job’s result appears as a status check: a yellow dot while it runs, then a green check or a red X. The Checks tab of the pull request shows the details.
  • A red X alone doesn’t stop anyone from clicking Merge. To make it required, add the rule Require status checks to pass before merging to your ruleset for main (Protecting main) and add the check named build (the job’s name). Then GitHub blocks the merge until the check passes, for everyone, AI agents included.

78.5 Secrets in GitHub Actions

As of Nov 24, 2026 · Official docs: Using secrets in GitHub Actions · Secrets

Never write a key in a workflow file: the file is in Git (.gitignore and Keeping Secrets Out of Git). Instead, store it as a repository secret: on the repository’s page, click Settings → Secrets and variables → Actions → New repository secret, type the name and the value, and click Add secret. The workflow refers to it as ${{ secrets.NAME }}. GitHub hides secret values in the logs, but the docs say that this hiding “is not guaranteed”, so never print a secret on purpose.

78.6 What it costs

As of Nov 24, 2026 · Official docs: GitHub Actions billing

  • Public repositories: standard GitHub-hosted runners are free.
  • Private repositories: each plan includes a monthly amount of compute, written in dollars: $12 on GitHub Free and $18 on GitHub Pro. A standard Linux runner costs $0.006 a minute, so that is about 2,000 or 3,000 minutes a month. A failed run counts too.
  • Without a payment method on file, GitHub blocks further runs when the included amount is used up.

A small team that builds only on pull requests and pushes to main usually stays inside these limits. An agent that pushes every few minutes all day may not.

78.7 Claude Code in CI

As of Nov 24, 2026 · Official docs: Claude Code GitHub Actions

Claude Code can also run inside a workflow: after /install-github-app, @claude in an issue or pull request comment starts a GitHub Actions job in which Claude works on the request (AI in the Pull Request Workflow). Each run uses Actions minutes and API tokens or your Claude subscription. To limit both, the docs suggest workflow timeouts and GitHub’s concurrency controls.

78.8 AI agents and the flood of pull requests

Coding agents write a draft in minutes, several can work at once (Running several agents at once), and each one commits, pushes and opens pull requests. Every push and pull request starts CI. GitHub’s own reports show the result:

  • More of everything. In the 12 months covered by Octoverse 2026 (published Oct 28, 2026), developers pushed to GitHub 17.9 billion times, “more than in 2024 and 2025 combined”; merged pull requests “more than tripled to 1.3 billion”; and Actions ran “more than three times last year’s total” of jobs. By September 2026, more than 40% of pull requests started with an agent’s first draft, up from 17% in March (GitHub Octoverse 2026).
  • Capacity problems. GitHub’s CTO wrote on Apr 28, 2026 that “agentic development workflows have accelerated sharply” since late December 2025. GitHub had started a plan in October 2025 to grow its capacity 10 times; by February 2026 it needed to “design for a future that requires 30X today’s scale” (An update on GitHub availability). A 7-hour-47-minute outage on Aug 17, 2026 stopped Actions, pull requests and more; GitHub called it a “capacity failure” (The August 17 outage, and the work ahead). On Oct 5, 2026, Actions jobs “stay[ed] queued much longer than usual” for more than three hours (Availability report: October 2026). See also The Pragmatic Engineer, May 7, 2026.
  • More minutes and money. More runs mean more CI minutes. Since June 1, 2026, even GitHub’s own AI reviewer (Copilot code review) uses Actions minutes in private repositories (GitHub changelog).
  • Review is the bottleneck. Agents open pull requests faster than people can read them, so pull requests wait longer, or are merged without a real review.

78.8.1 What teams do about it

Practice How
Run only the checks you need Path filters (paths-ignore) skip a workflow when only, for example, documentation changed (see the warning below)
Cache dependencies cache: npm in actions/setup-node
Cancel outdated runs concurrency with cancel-in-progress: true: a new push to a branch cancels its older, unfinished run
Stop runaway jobs timeout-minutes on the job
Keep pull requests small One feature or fix per pull request; tell your agent the same in CLAUDE.md
Require checks A ruleset with Require status checks to pass before merging
Use a merge queue GitHub tests queued pull requests together against the newest main (only in an organization’s public repositories, or private ones on GitHub Enterprise Cloud; not in a personal account’s repositories)
Review every AI pull request A teammate reads and runs it before it is merged

As of Nov 24, 2026 · Official docs: Control workflow concurrency · Managing a merge queue

The first workflow with a concurrency group and a time limit (it also passes actionlint):

name: CI

on:
  push:
    branches: [main]
  pull_request:

concurrency:
  group: ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: true

jobs:
  build:
    runs-on: ubuntu-latest
    timeout-minutes: 10
    steps:
      - uses: actions/checkout@v7
      - uses: actions/setup-node@v7
        with:
          node-version: 24
          cache: npm
      - run: npm ci
      - run: npm run build
      - run: npm test --if-present
Path filters and required checks

GitHub’s docs say that when a path filter skips a workflow, its checks stay “Pending”, and a pull request that requires them can’t be merged. The docs advise against requiring workflows that can be skipped. So if build is a required check, don’t add paths-ignore to its workflow.

78.9 Key takeaways

  • CI builds and tests every push and pull request. Continuous delivery waits for a person to release; continuous deployment releases automatically.
  • Vercel already deploys every push; GitHub Actions adds tests and a check that a ruleset can require before a merge.
  • A workflow is a YAML file in .github/workflows/; keys go in repository secrets, never in the YAML.
  • AI agents multiply pushes and pull requests: more CI runs, cost, queues and review work. Cancel outdated runs, cache, keep pull requests small, require checks, and have a person review every AI pull request.

Practice Questions

Easy

Question 1 · Short answer

What does continuous integration (CI) do each time someone pushes or opens a pull request?

Suggested answer

A clean computer automatically downloads the code, installs the packages, builds the app and runs the tests (and often a linter). The team sees the result within minutes, so problems are found while the change is small.

Question 2 · Multiple choice

What is the difference between continuous delivery and continuous deployment?

  1. Continuous delivery runs tests; continuous deployment doesn’t.
  2. In continuous delivery, a person decides when a tested change goes live; in continuous deployment, it goes live automatically.
  3. Continuous delivery is for websites; continuous deployment is for phone apps.
  4. There is no difference; they are two names for CI.
Suggested answer

b. Both build and test every change. Delivery stops at “ready to release” and waits for a person; deployment releases automatically. a is wrong because both run tests, c is invented, and d is wrong because CI is the checking part, not the release part.

Question 3 · Matching

Match each term with its meaning.

# Term Letter Meaning
1 Workflow A A virtual machine that runs one job and is then deleted
2 Trigger (on:) B One command or one action inside a job
3 Runner C A YAML file in .github/workflows/
4 Step D The event that starts the workflow, such as push
Suggested answer

1 → C, 2 → D, 3 → A, 4 → B.

Question 4 · True or false

“My final project is on Vercel, so it already has continuous deployment.”

Suggested answer

True. Vercel builds every push. A successful build of main goes live automatically, and other branches and pull requests get preview deployments. What Vercel doesn’t do is run your tests or block a merge; that’s what CI adds.

Question 5 · Fill in the blank

GitHub finds workflow files only in the folder ________ of the repository.

Suggested answer

.github/workflows/ (the file names end in .yml or .yaml).

Question 6 · Short answer

Where do you look on GitHub to read the log of a workflow run?

Suggested answer

In the repository’s Actions tab: click the run, then the job (for example build), then the step. From a pull request, the Checks tab (or the check’s Details link) leads to the same log.

Medium

Question 7 · Read the config

In the workflow on this page, which events start a run? Does a push to a branch named add-pricing start one if there is no pull request for it?

Suggested answer

A push to main, and every pull request (opening it and each new push to it). A push to add-pricing alone does not start a run, because push: is limited to branches: [main]. As soon as someone opens a pull request for add-pricing, the pull_request trigger runs it.

Question 8 · Predict the output

A project’s package.json has no test script. What happens in CI with npm test, and with npm test --if-present?

Suggested answer

npm test fails with Missing script: "test", so the step and the check fail. npm test --if-present does nothing and succeeds, so the job goes on.

Question 9 · Scenario

Sam’s pull request shows a red X next to build. On his laptop, npm run dev works. What should he do?

Suggested answer

Open the check’s log (Actions tab, or Details on the pull request), find the first failed step and its first error. Run the same command, npm run build, on his laptop: the dev server doesn’t type-check the whole app the way a build does. Typical causes are a type error, a file he forgot to commit, a package missing from package.json, or an environment variable the runner doesn’t have. He fixes it, commits and pushes to the same branch; the check runs again. He can paste the error into Claude Code for an explanation.

Question 10 · Find the bug

What is wrong with this step, and how do you fix it?

      - run: npm run build
        env:
          OPENAI_API_KEY: sk-proj-abc123
Suggested answer

The key is written in the workflow file, which is in Git (and public in a public repository). Revoke that key and make a new one. Store the new value as a repository secret (Settings → Secrets and variables → Actions → New repository secret) named OPENAI_API_KEY, and write OPENAI_API_KEY: ${{ secrets.OPENAI_API_KEY }} instead.

Question 11 · Short answer

The check on Maria’s pull request is red, but the Merge button still works. Why, and how can the team change that?

Suggested answer

A check only reports a result; by itself it doesn’t block anything. The team adds the rule Require status checks to pass before merging to the ruleset for main and adds the check build. Then GitHub blocks the merge until the check passes. (In a private repository, GitHub enforces rulesets only on paid plans; students can get GitHub Pro free through GitHub Education.)

Question 12 · Short answer

What does this part of a workflow do, and why does it save CI minutes?

concurrency:
  group: ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: true
Suggested answer

It puts all runs of this workflow for the same branch into one group. When a new run starts, GitHub cancels the older run of that branch that is still in progress. If an agent pushes three times in two minutes, only the newest commit is fully built and tested, instead of three runs.

Question 13 · Short answer

As of Nov 24, 2026, what do GitHub Actions minutes on standard runners cost a public repository, and what limits a private repository on GitHub Free?

Suggested answer

They are free for public repositories. A private repository on GitHub Free gets $12 of included compute a month (about 2,000 minutes on a standard Linux runner at $0.006 a minute). Without a payment method, GitHub blocks further runs when that amount is used up.

Hard

Question 14 · Long answer

Explain how AI coding agents put pressure on GitHub and on CI/CD pipelines. Use at least two facts from GitHub’s own reports.

Suggested answer

Agents write code fast, run in parallel, and commit, push and open pull requests often. Every push and pull request starts CI, so there are more runs, more minutes and more cost, longer queues for runners, and more pull requests for people to review. Facts a good answer can use: in Octoverse 2026, merged pull requests more than tripled to 1.3 billion, Actions ran more than three times as many jobs, and by September 2026 more than 40% of pull requests started with an agent’s first draft; GitHub’s CTO wrote that it had to design for 30 times its scale; the Aug 17, 2026 outage was a capacity failure that stopped Actions and pull requests; on Oct 5, 2026, Actions jobs stayed queued for hours.

Question 15 · Scenario

A team lets Claude Code open a pull request for every small fix. They now have 25 open pull requests, a review queue nobody keeps up with, and their private repository used most of its Actions minutes in two weeks. Suggest four changes and explain each.

Suggested answer

Any four of these, with reasons:

  • Group related fixes into fewer, focused pull requests (and say so in CLAUDE.md): fewer runs and fewer reviews.
  • Cancel outdated runs with concurrency and cancel-in-progress: true: only the newest push of each branch uses minutes.
  • Cache dependencies (cache: npm): each run installs faster.
  • Path filters: don’t run the build when only documentation changed (but not on a workflow whose check is required: its check would stay “Pending” and block the merge).
  • timeout-minutes: a stuck job can’t use hours.
  • A person reviews each AI pull request before it is merged, and the team limits how many open pull requests each person may have.
  • Make the repository public: standard runners are free there (if nothing secret is in the code).

Question 16 · Compare

Vercel already builds every pull request. Why might a team still add a GitHub Actions workflow? Give two reasons, and one reason a small team might skip it.

Suggested answer

Reasons to add it: Vercel builds the app but doesn’t run the tests or the linter; a workflow can run them. The workflow’s build check can be made required in a ruleset, so nobody (and no agent) can merge a pull request that fails. CI also works the same for every teammate, whoever owns the Vercel project. A reason to skip it: if the app has no tests yet, the workflow repeats the build that Vercel already does, and it uses Actions minutes in a private repository.

Question 17 · Scenario

Maria adds the workflow to the task app. The run fails at npm run build with TypeError: Invalid URL, but the same build works on Vercel. Explain why and what to do.

Suggested answer

The task app reads NEXT_PUBLIC_SUPABASE_URL in next.config.mjs while it builds. Vercel has that variable in its project settings, and Maria has it in .env.local, but the GitHub runner has neither. Question 18 · Short answer

Why can’t a student team use GitHub’s merge queue for a repository in one student’s personal account, and what does a merge queue do?

Suggested answer

As of Nov 24, 2026, merge queues are available only in public repositories owned by an organization, and in private repositories of organizations on GitHub Enterprise Cloud. A merge queue takes pull requests that passed their checks, tests them together against the newest main, and merges them in order, so a busy main is never broken by two changes that each passed alone.
